# 用户蒸馏与人物画像系统设计方案

## 1. 背景与目标

### 1.1 问题

当前 Mona 在长期使用中缺乏对用户的持续理解能力：

- `memory/user_profile.md` 是手填的静态画像，无法随使用自动演化
- 已有大量用户数据（笔记、邮件、对话历史、工具调用记录）未被蒸馏利用
- AI 上下文中没有"用户是谁、关注什么、怎么工作"的稳定信号

### 1.2 目标

通过定期蒸馏机制，让 Mona 在长期使用过程中：

1. **越来越懂用户**：基于行为数据自动更新画像
2. **形成人物画像**：可视化呈现"AI 眼中的我"
3. **形成成长轨迹**：可视化呈现用户随时间的关注领域、技能积累变化
4. **辅助 AI 决策**：将精炼画像按需注入 AI 上下文，提升个性化响应质量

### 1.3 与女娲.skill 的区别

| 维度 | 女娲（名人蒸馏） | Mona（用户蒸馏） |
|------|---------------|---------------|
| 数据来源 | 公开著作/演讲 | 私有笔记+邮件+对话历史 |
| 数据性质 | 静态、有限、已成型 | 持续增长、动态变化 |
| 蒸馏时机 | 一次性（离线） | 持续性（在线增量） |
| 独特性 | 无（开源可复制） | 极强（数据壁垒不可复制） |
| 产品定位 | 玩具/炫技 | 核心护城河 |

**结论**：用户蒸馏价值远高于名人蒸馏。名人蒸馏是静态归纳，用户蒸馏是动态成长，是 Mona 从"工具"升级为"伙伴"的关键差异化能力。

## 2. 数据源分析

### 2.1 已有的天然蒸馏数据源

| 数据源 | 位置 | 反映的用户维度 |
|--------|------|---------------|
| 笔记 | notes vault | 用户深度思考的产物、认知结构、知识领域 |
| 邮件 | email_intel DB | 往来通信、协作网络、邮件约定/截止日期 |
| 收藏记忆 | hoard/ | 跨源 URL/片段收藏，反映关注点 |
| Agent 对话历史 | session/ | 用户在什么场景下需要什么帮助 |
| 工具调用记录 | (需新增采集) | 高频任务类型、工具链偏好 |
| 长期记忆 | memory/ | 用户已显式记录的偏好、人格 |

**关键洞察**：缺的不是数据，是定期蒸馏机制。Mona 已在持续收集数据，只是没有汇总归纳。

### 2.2 数据采集现状

- ✅ 笔记：已索引，支持 hybrid search
- ✅ 邮件：已分析（意图/紧急度/分类），可查询
- ✅ hoard：已聚合跨源数据
- ⚠️ 工具调用历史：散落在 session 文件中，**需新增聚合采集**
- ⚠️ 对话主题分类：**需新增 LLM 调用归类**

## 3. 架构设计

### 3.1 核心原则：双存储分离

AI 上下文成本与前端展示丰富度存在天然冲突，采用双存储分离解决：

```
user_profile.md（AI 按需读取，精炼）
├─ facts 段：身份、技术栈、偏好
├─ current_focus 段：当前关注（由轨迹切片更新）
└─ work_patterns 段：高频任务、工具链偏好

profile.rich.json（前端专用，丰满，不进 AI 上下文）
├─ facts 镜像
├─ evidence 聚合：笔记分布、邮件主题、调用记录明细
├─ trajectory：时间序列数据点
└─ visualizations：预计算的图表数据
```

**两者由同一个蒸馏任务产出，原子写入两个文件**：
- 蒸馏后提取 facts → 更新 `user_profile.md`
- 蒸馏全量结果 → 写入 `profile.rich.json`

### 3.2 数据流

```
[笔记/邮件/hoard/对话/工具调用]
              ↓
       [定期蒸馏任务 (cron)]
              ↓
    ┌─────────┴─────────┐
    ↓                   ↓
 user_profile.md   profile.rich.json
 (AI 按需读取)      (前端展示)
    ↓
 identity.md 引导 Agent 用 memory_read(file="user") 读取
```

### 3.3 AI 注入策略

- **identity.md 不变**：保持当前轻量引导方式（已引导 Agent 用 `memory_read(file="user")` 按需读取）
- **画像摘要**：核心几条可轻量注入 system prompt（可选）
- **画像详情**：Agent 按场景按需读取对应段落（如技术问题只读 facts 段）
- **轨迹**：**不注入 AI**，原因：
  1. 时间序列数据 token 成本高，ROI 低
  2. 刻板印象风险：AI 看到"用户不擅长 X"会持续按旧认知对待
  3. 轨迹价值在激励用户，不是给 AI 标签
- **轨迹最新切片**：可作为"画像当前关注段"注入，因为本质是 facts

## 4. 用途矩阵

| 内容 | 前端展示 | 注入 AI |
|------|:------:|:------:|
| 画像全文 | ✅ | 按需（`memory_read`） |
| 画像摘要（核心几条） | - | ✅ system prompt 轻量注入 |
| 成长轨迹 | ✅ | ❌ |
| 轨迹最新切片 | - | ✅ 但作为"画像当前关注段"注入 |

## 5. 实现路线（三阶段）

### 阶段 1：工作模式蒸馏（优先）

**目标**：基于 Agent 对话历史 + 工具调用模式，回答"这个用户经常让我做什么？"

**蒸馏内容**：
- 高频任务类型（写代码 / 整理邮件 / 总结文档 / 查笔记）
- 常用工具组合（A→B→C 的调用链）
- 偏好的输出风格（简洁 / 详细 / 是否带 emoji）

**落地**：
- 新增 cron 任务定期蒸馏
- 写入 `user_profile.md` 的 `## Work Patterns` 段
- 前端先不做展示，验证 AI 行为改善

**验证标准**：用户主观感受"AI 更懂我的工作习惯了"

### 阶段 2：人物画像（中期）

**目标**：基于 notes + email 内容聚类，回答"这个用户是谁？"

**蒸馏内容**：
- 关注领域（技术栈、行业、兴趣）
- 人际网络（常联系谁、协作模式）
- 知识结构（笔记分类、深度分布）
- 工作节奏（活跃时段、邮件回复模式）

**落地**：
- 写入 `user_profile.md` 的 `## Profile` 段
- 同步写入 `profile.rich.json` 的 facts + evidence 段
- **前端可视化**：基础画像卡片（关注领域标签云、人际网络简图）

**验证标准**：用户在 UI 上看到"AI 眼中的我"，并能修正

### 阶段 3：成长轨迹（远期）

**目标**：基于时间序列对比，回答"这个用户在成长吗？"

**蒸馏内容**：
- 关注领域变化（3个月前 vs 现在的笔记主题分布）
- 技能积累曲线（某领域笔记密度增长）
- 工作模式进化（从被动求助 → 主动规划）

**落地**：
- 写入独立的 `profile.rich.json` 的 trajectory 段
- **前端可视化**：时间轴、雷达图、热力图、密度曲线

**验证标准**：用户能直观看到自己的成长轨迹，产生情感价值

## 6. 关键设计原则

### 6.1 蒸馏结果人类可读可改
- 画像全文必须在 UI 上可见
- 用户能直接编辑修正（修正后写回 `user_profile.md`，下次蒸馏保留用户修改）
- 不能黑盒

### 6.2 隐私边界显式
- 用户能选择哪些数据参与蒸馏（如不蒸馏私人邮件）
- 蒸馏配置在 settings 中可调
- 敏感字段（如人际网络）默认关闭，需用户主动开启

### 6.3 渐进式上线
- 不急着做满，先做阶段 1 验证价值
- 每阶段独立交付，失败可回滚
- 用户感知到价值后再扩展

### 6.4 蒸馏成本可控
- 定期（如每周）而非实时
- 大数据先用本地聚类/统计，再 LLM 归纳
- LLM 调用限于"总结性"步骤，不做逐条分析

## 7. 技术实现要点

### 7.1 蒸馏任务调度

复用现有 cron 系统（`mona/cron/`），新增蒸馏任务：
- 触发：每周日凌晨 3:00
- 输入：过去 7 天的笔记/邮件/对话/工具调用聚合
- 输出：增量更新画像，追加轨迹数据点

### 7.2 工具调用历史采集（需新增）

当前工具调用记录散落在 session 文件中，需要：
- 新增聚合器：扫描指定时间段的 session，提取 tool_call 事件
- 输出结构化数据：`{tool_name, called_at, params_summary, success}`
- 存储为中间文件供蒸馏任务读取

### 7.3 蒸馏 LLM Prompt 设计

蒸馏 prompt 示例（阶段 1）：

```
你是用户行为分析师。基于以下聚合数据，归纳用户的工作模式：

【对话主题分布】
{topic_distribution}

【工具调用 Top 10】
{top_tools}

【工具调用链模式】
{tool_chains}

请输出 JSON：
{
  "frequent_tasks": ["..."],
  "preferred_tools": ["..."],
  "output_style": "concise|detailed|...",
  "confidence": 0.0-1.0
}
```

### 7.4 前端可视化（阶段 2/3）

#### 入口位置

侧边栏一级入口精简为 5 项：Mona / 笔记 / 终端 / 邮件 / 日程。数据库、知识库、PPT制作收纳进"更多"二级菜单（已实施，见 `webui/src/components/Sidebar.tsx`）。

用户蒸馏可视化作为**新的侧边栏一级入口**，与其他 5 个并列。图标用人物/头像图标，排在日程之后、"更多"之前。这样保证主入口视觉冲击力，画像页有全屏展示空间。

```
侧边栏一级入口（6 项）:
├─ Mona
├─ 笔记
├─ 终端
├─ 邮件
├─ 日程
├─ 画像（新增，人物图标）  ← 用户蒸馏入口
└─ 更多（DropdownMenu 二级）
   ├─ 数据库
   ├─ 知识库
   └─ PPT制作
```

#### 页面整体布局

借鉴 Linear / Vercel Dashboard / Apple Health 的设计语言：

```
┌─────────────────────────────────────────────┐
│ 顶部：用户头像 + 标语 + 蒸馏时间戳            │
├─────────────────────────────────────────────┤
│ Tab 切换：[人物画像] [成长轨迹] [工作模式]   │
├─────────────────────────────────────────────┤
│                                             │
│  Tab 内容区（酷炫可视化）                    │
│                                             │
└─────────────────────────────────────────────┘
```

#### 人物画像 Tab

| 可视化 | 图表类型 | 数据源 |
|--------|---------|--------|
| 关注领域 | 标签云（带颜色权重，font-size 随频率变化） | notes 分类聚合 + email 主题分类 |
| 技术栈分布 | 雷达图（5-8 维评分，0-10） | notes 技术词汇频率 + 工具调用类型 |
| 人际网络 | 力导向关系图（节点=联系人，边=邮件往来，节点大小=交互频次） | email_intel 发件人聚合 |
| 知识结构 | 堆叠条形图（按笔记本分类，堆叠=标签细分） | notes vault 元数据 |

#### 成长轨迹 Tab

| 可视化 | 图表类型 | 数据源 |
|--------|---------|--------|
| 活跃度热力图 | GitHub 贡献图风格（日历热力图，颜色深浅=当天活动量） | 笔记/邮件/对话总数（按日聚合） |
| 关注领域演变 | 多线折线图（每条线=一个领域，横轴=时间） | 按月聚合的 notes 主题分类 |
| 技能积累曲线 | 堆叠面积图（按月堆叠，每层=一个领域） | notes 标签按月统计 |
| 关键里程碑 | 时间轴（首次笔记、首次邮件、领域切换等） | 系统事件日志 |

#### 工作模式 Tab

| 可视化 | 图表类型 | 数据源 |
|--------|---------|--------|
| 高频工具调用 Top 10 | 横向条形图（带数字滚动动画） | tool_call 历史聚合 |
| 工具调用链 | 桑基图 Sankey（A→B→C 流向，宽度=频次） | tool_call 序列模式 |
| 活跃时段 | 热力图（24h × 7d 网格） | 按小时+周几聚合的调用次数 |
| AI 协作模式 | 环形图（主动求助 vs 被动响应比例） | 对话开始类型分类 |

#### 视觉风格

- 深色背景为主，复用现有暗色主题
- 数据点用渐变色 + 发光效果（`box-shadow` + `filter: blur()`）
- 卡片用毛玻璃（`backdrop-blur` + 半透明背景）
- 关键指标大字号呈现（如"已蒸馏 142 天"用 48px 字号）
- 进度环/雷达带过渡动画（`Framer Motion` 入场动画）

#### 技术栈选型

| 需求 | 推荐库 | 理由 |
|------|--------|------|
| 基础图表（条形/折线/面积/雷达） | **Recharts** | React 生态成熟，Tauri 兼容好 |
| 关系网络图 | **react-force-graph** 或 **Cytoscape.js** | 力导向布局效果好 |
| 桑基图 / 复杂热力图 | **D3.js** 直接用 | 灵活度高，定制性强 |
| 入场/切换动画 | **Framer Motion** | Tab 切换、数字滚动、卡片入场 |
| 日历热力图 | **react-calendar-heatmap** | GitHub 风格现成方案 |

**推荐组合**：Recharts（主力，覆盖 70% 图表）+ Framer Motion（动画）+ D3.js（桑基图、热力图定制）+ react-calendar-heatmap（贡献图）

#### 数据接口

- 新增 HTTP 路由（gateway port）：
  - `GET /api/profile` → 返回 `profile.rich.json` 全量
  - `GET /api/profile/trajectory?from=...&to=...` → 返回时间序列切片
  - `PATCH /api/profile/facts` → 用户手动修正画像（写回 `user_profile.md`）
- 路由注册在 `mona/api/server.py` 的 `create_app()` 中（POST/PUT/PATCH 必须在 gateway）
- 前端用 `getGatewayHttpBase()` 获取基础 URL

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 数据一致性：两文件不同步 | AI 看到的和用户看到的不一致 | 同一蒸馏任务原子写入两文件 |
| 存储冗余：facts 镜像重复 | 几 KB 级别，可接受 | 不处理 |
| 蒸馏结果不准 | 误导 AI 决策 | 用户可修正，修正项有标记，下次蒸馏保留 |
| 隐私泄露 | 敏感信息进入画像 | 隐私边界显式配置，默认关闭敏感字段 |
| 蒸馏成本失控 | LLM 调用过多 | 先本地统计聚类，LLM 只做总结 |
| 刻板印象 | AI 按旧画像对待用户 | 轨迹不注入 AI，画像定期覆盖更新 |
| 用户感知不到价值 | 功能闲置 | 阶段 1 先验证 AI 行为改善，再做前端展示 |

## 9. 验证与度量

### 9.1 阶段 1 验证
- 用户主观反馈：AI 是否更懂工作习惯
- 工具调用准确率：相关工具是否被更主动调用
- 画像置信度：蒸馏结果的 confidence 分数

### 9.2 阶段 2 验证
- 前端画像页访问量
- 用户修正频率（过高说明蒸馏不准）
- 画像注入后对话质量评分（A/B 测试）

### 9.3 阶段 3 验证
- 轨迹页停留时长
- 用户分享/截图行为（情感价值指标）
- 留存率对比（有轨迹 vs 无轨迹用户）

## 10. 与现有系统的关系

### 10.1 identity.md
- **不变**：保持当前轻量引导
- 已有 `## Personal Knowledge Sources` 引导 Agent 按需查询笔记/邮件/hoard
- 画像通过 `memory_read(file="user")` 工具按需读取，不直接进 system prompt

### 10.2 memory 系统
- `user_profile.md` 是 memory 系统的一部分
- 蒸馏任务通过 `memory_edit(file="user", ...)` 写入
- 保留用户手填段落，蒸馏只更新特定段

### 10.3 cron 系统
- 蒸馏任务复用 cron 调度
- 通过 `mona/cron/service.py` 注册定时任务

### 10.4 前端
- 新增画像/轨迹页（路由待定，建议放在设置或独立入口）
- 复用现有 UI 组件库
- 数据通过新增 HTTP 路由提供（gateway port）

## 11. 待确认事项

1. **画像页入口位置**：放在设置内、独立侧边栏入口、还是独立窗口？
2. **隐私配置粒度**：按数据源（笔记/邮件/hoard）配置，还是按字段（人际网络/工作模式）配置？
3. **阶段 1 优先级**：是否作为下一个迭代的高优先级？还是先观察 identity.md 改动效果再启动？
4. **工具调用历史采集**：是否需要新增独立存储，还是每次蒸馏时扫描 session？
5. **轨迹数据保留策略**：永久保留，还是滚动保留最近 N 个月？
