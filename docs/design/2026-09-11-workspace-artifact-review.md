# 工作区、会话与产物机制审计

- 日期：2026-09-11
- 范围：当前工作树的 Agent、项目、协作房间、工具产物、前端工作区及真实音乐家会话。
- 结论：按所有者保存文件、按会话投影归属的方向合理；目录、归属、版本和导出尚未形成完全一致的契约。本轮修复目录展示错误，不进行文件迁移或全面重构。

## 1. 当前目录与会话关系

以下 `W` 是配置中的 Mona 工作区根目录，默认 `~/.mona/workspace`；`P` 是用户绑定的项目目录。它们不是同一层概念。

| 场景 | 实际执行与默认写入目录 | 展示与隔离语义 |
|---|---|---|
| 普通 Mona 会话 | `W/agent-workspaces/mona/output` | 多个 Mona 会话共享文件目录；交付和过程记录按会话/任务区分 |
| 专家私聊，如音乐家 | `W/agent-workspaces/<agent_id>/output` | 不同专家目录分开；同一专家多个私聊共享目录 |
| Mona 或专家的项目会话 | `P`，直接采用 `metadata.workspace` | 同一项目的会话共享实际项目文件；工作区列项目清单 |
| 协作房间的普通 Agent Job/工作流步骤 | 执行者自己的 `agent-workspaces/<agent_id>/output` | 房间聚合明确引用，不扫描所有成员目录，也没有独立房间产物副本 |
| 房间绑定工作区 | 将绑定目录作为 Agent 输出目录的基址 | 与普通项目会话直接在 `P` 工作的含义不同 |
| 股票专用流程 | `W/stock_projects/<run_id>` | 产品持有运行目录，已有运行级物理分离 |
| 视频专用 Document Agent | 默认使用 `W`，由工具/工作流写 `video_projects/` | 专用产品工作台管理，不能假定所有文件都在聊天的 Agent output |
| 普通 `spawn` 子任务 | 继承调用方当前工作区 | 不因启动子任务而创建独立目录；命名专家 Job 则按上面的 Agent/产品规则路由 |

入口证据：[AgentLoop._effective_workspace](../../mona/agent/loop.py)、[子任务路由](../../mona/agent/subagent.py)、[统一路径助手](../../mona/config/paths.py)。工具执行通过 [ContextVar](../../mona/agent/tools/path_utils.py) 读取当前工作区，进入会话时设置，退出时复原。

会话、产物和私有资源还存在三个不同持久层：模型会话在 `W/sessions`，WebUI 事件在实例数据目录 `webui`；Agent 私有记忆/Skill/知识在实例数据目录 `agents/<id>`；Job/Workflow/Run 状态在实例数据目录 `runtime`。它们不应进入用户产物目录。可下载运行时继续遵循独立运行时仓库规则。

## 2. 不同产物入口

| 入口 | 落盘或文件来源 | 如何出现在产品中 |
|---|---|---|
| `write_file` / `edit_file` / `apply_patch` | 当前工作区内的相对路径或允许的绝对路径 | 成功文件操作提供过程证据；目录扫描发现文件；明确交付另走 `deliver_file` |
| `exec` 执行脚本、CLI、Skill | 默认 cwd 跟随当前工作区；可按工具规则指定 cwd | 目录可见不依赖交付；任意子进程写入不能单靠扫描证明属于当前任务 |
| `deliver_file` | 引用已经存在的文件，本身不复制文件 | 发出明确交付事件，生成 `ArtifactRef`，概览显示交付物 |
| `message(media=...)` | 当前工作区解析本地媒体，也可引用远程媒体 | 消息附件路径；不等同于统一的产物登记或搬入 output |
| 生图/生视频工具 | 由生成工具保存结果 | Runner 识别结构化生成结果后自动调用交付工具；仍可能出现生成成功但交付登记失败 |
| 图表、数据处理、文档工具 | 通过当前工作区解析输出路径 | 返回文件路径/结构化结果；落盘、过程证据、明确交付是不同阶段 |
| 可编辑画布 | 当前工作区下的 `.mona-canvas`，通常位于 `canvases/` | 按 `originChatId` 恢复会话画布；目录清单仍能显示真实文件 |
| Office 协作 | Services 维护编辑会话/checkpoint；Gateway 将导出字节写入当前工作区 | 打开编辑会话不代表已经存在 output 文件；导出后才有本地文件 |
| 音乐家 ABC | 通用文件工具写 `.abc`；音乐工具只读取检查；交付前做乐谱校验 | 本次两份文件均已明确交付，应同时存在于目录视图和概览交付物 |
| 前端手动导出 MIDI/MP4、Office 等 | 系统保存对话框选定的路径 | 写在工作区外就不会被其扫描发现；这是用户选择的外部导出位置，不能推断为 Agent 目录产物 |
| 用户上传/粘贴附件 | 首先暂存 `W/uploads/<chat_id>` 等输入路径，运行时按需要放入活动工作区 | 输入附件不应因为上传而自动变成交付物 |
| 外部软件/用户手工放入目录 | 由用户或外部程序决定 | 工作区扫描可发现，但没有会话/任务归属证据 |
| 浏览器截图、终端报告 | 浏览器截图或报告使用系统临时目录 | 属于工具/产品结果，未经明确保存不在 Agent 目录扫描范围内 |
| 笔记保存图片、视频抽帧 | 笔记仓库 `assets` | 应由笔记模块持有，不应为了工作区可见而复制所有笔记资产 |
| 学术研究 | 当前工作区的 `research/` 等路径 | 目录可见，明确交付仍需对应记录 |

主要入口：[filesystem](../../mona/agent/tools/filesystem.py)、[shell](../../mona/agent/tools/shell.py)、[deliver_file](../../mona/agent/tools/deliver_file.py)、[message](../../mona/agent/tools/message.py)、[生成结果登记](../../mona/agent/runner.py)、[Office 工具](../../mona/agent/tools/office.py)、[乐谱导出](../../webui/src/components/deliver/MusicScorePreview.tsx)、[上传与扫描](../../mona/channels/websocket.py)。

## 3. 音乐家文件不可见的根因及修复

真实磁盘扫描得到 `autumn_memories.abc` 与 `autumn_memories_v2.abc`；音乐家会话没有项目绑定，两个文件的交付记录均属于 `com.mona.musician`。路径选择与文件生成在此案例中正常。

原后端响应把目录清单定义成：

```text
files = 扫描文件 - 当前会话交付文件 - 当前任务过程文件
```

这适用于过去在同一个面板里互斥分组的展示方式。独立“工作区”标签直接渲染 `files` 后，两份乐谱都已交付，清单自然为空。前端另外还有按归属减去文件的旧逻辑，影响目录数量和预览导航。

本轮改为：

```text
工作区 files = 当前所有者目录的完整扫描结果
概览 session_files = 当前会话明确交付记录
概览 task_files = 当前任务成功操作记录中、尚未明确交付的现存文件
```

同一文件可以同时出现在目录视图和交付视图；概览内部仍不重复。房间保持明确引用投影，项目保持绑定目录扫描；无证据文件不会被归入当前任务。

还修复了首次请求失败时的错误丢失：原 `useArtifacts` 仅允许“已经成功加载过的来源”展示错误，第一次请求失败就会显示成空目录。现在错误也绑定请求来源，能显示并通过刷新重试。

## 4. 设计判断与剩余缺口

### 应保留的设计

1. **文件按所有者持久保存，会话保存引用。** 减少无意义复制，允许同一 Agent 跨会话复用成果；删除/归档会话与删除文件应继续分开考虑。
2. **项目直接使用真实目录。** 用户能用现有编辑器、Git 和终端处理文件，不需要创建平行项目副本。
3. **目录扫描不证明任务归属。** 当前精确 `task_id` 和明确交付事件的方向正确，不能倒退为按 mtime 或扫描差分认领文件。
4. **房间聚合引用。** 保留创建者及 Job/Run 线索，比复制全部成员产物或扫描所有 Agent 更清晰。

### 需要后续收敛的问题

| 优先级 | 已核实的现状 | 影响与最小建议 |
|---|---|---|
| 高 | `ArtifactRef.owner_kind` 只有 agent/product；`deliver_file` 却以项目活动目录生成 agent 类型相对路径，`owner_root()` 又固定解析到 Agent output | 项目文件的结构化引用不能独立往返还原原路径。当前项目预览依靠 `scope=project + session_key` 的另一条分支正常工作，不能据此认为引用模型完整。补项目所有者与受控解析，验证生成、历史恢复、预览使用同一根目录 |
| 高 | 同一 Agent 的会话与普通工作流重复运行共享可变文件；引用没有内容快照或版本哈希 | 文件同名可能覆盖，旧会话点开的可能是最新内容。覆盖属于代码机制允许的风险，本次未证实用户文件被覆盖。优先给新任务/运行的新增产物稳定子目录或冲突命名，明确保存同名文件时再更新 |
| 中 | 根目录规则分散于 Python loop、WebSocket、前端 `buildSharedOutputDir`；右侧终端默认用配置根 `W`，Agent 普通任务用 Agent output | 同一会话的“打开目录”、创建画布、Office 导出、终端容易分叉。优先由后端返回已解析的活动根与所有者，前端消费；右侧终端使用同一活动根 |
| 中 | `ArtifactRef` 表示指向当前文件的引用，目录 rename 只更新部分任务事件，历史交付引用与文件移动之间没有统一管理 | 改名/移动后旧交付可能显示已移除；不要向用户承诺引用等价于版本快照。需要对改名、删除、再次生成同一路径补行为契约 |
| 中 | 后端每 2 秒聚合轮询所有 Agent output 并广播变化；项目侧不订阅这个刷新通知 | Agent 文件多时扫描成本增长，外部项目编辑不一定及时反映。优先按活动所有者定向刷新，项目提供明确刷新能力；规模有证据后再引入增量监听 |
| 已处理 | 工作区原先跳过点文件、链接、临时文件、媒体 sidecar，项目还跳过依赖/构建目录，空文件夹也不返回 | 已改为资源管理器语义：全部名称和类型均进入清单，目录及空目录作为条目返回；链接显示但不递归。仍保留 1000 条性能上限并明确提示，后续文件规模需要时改为按目录懒加载或分页 |
| 已处理 | `_scan_files` 原先对目录枚举的 `OSError` 统一跳过 | 根目录缺失或不可访问现在返回扫描失败并由工作区显示错误；子目录内单个条目在扫描时消失仍按文件系统竞态跳过 |
| 已处理 | 取消过滤后若仍先递归完整项目再截取 1000 条，大型项目会长时间保持空清单；前端又会把请求中的空数组显示成“暂无文件” | 扫描改为确定性的广度优先遍历，并在取得 1001 条时立即停止；前端加载期间不再显示空状态。真实 `oeagent` 项目由超过 30 秒未完成降至约 0.1 秒返回 1000 条并明确标记截断 |
| 中 | 生成、文件写入、显式交付、手动导出使用不同的事件路径 | 不应要求每种入口都靠模型记住调用交付工具。对能返回确定输出清单的生产者复用现有登记链路；外部保存仅按真实操作记录关联，不能从任意 shell 文本猜产物 |

引用缺口可由最小试验复现：在临时 `P/report.md` 上调用 `ArtifactRef.for_path(owner_kind="agent", root=P, ...)`，再分别用配置根或项目根调用 `resolve()`，两者都不等于原文件。项目界面的绕过分支位于 WebSocket 文件预览 `scope == "project"`。

路径隔离也不等于操作系统级安全沙箱：文件边界受现有 `restrict_to_workspace` 等配置影响，公共媒体目录等有明确例外。不能因为 Agent 使用独立 output 就宣称进程已被隔离。

## 5. 建议的实施顺序

1. 本轮完成目录/概览契约修复及首次扫描错误展示，确保现有音乐文件可见。
2. 下一轮只收敛活动根与项目引用：一个后端解析结果供工具与 UI 消费，补齐项目引用往返测试，同时对齐终端/导出目录。
3. 再处理重复任务与历史版本：先采用稳定运行目录/明确冲突规则，不立即引入全局产物数据库或全量快照系统。
4. 最后根据实际文件规模调整扫描、分页与定向通知；不为本次两个文件不可见引入新索引服务。

没有必要把每个会话都改成独立实体工作区，也没有必要让所有工具使用同一物理目录。需要统一的是“谁拥有、相对哪个根、由哪个任务产生、展示哪一种视图”。
