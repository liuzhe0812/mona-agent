📦 项目定位与架构
项目定位 面向开发者的单 Agent 编码助手框架，核心是 AgentLoop + AgentRunner 的双层架构 面向终端用户的多 Agent AI 助手平台，定位"AI 团队"，包含完整的桌面/Web/移动端产品 方向不同 Mona 偏底层框架，OpenAkita 偏完整产品；Mona 更轻量专注，OpenAkita 功能更全面
技术栈 Python (asyncio)，无前端框架，CLI + WebSocket 为主 Python (FastAPI + asyncio) 后端 + React/TypeScript 前端 + Tauri 2.x 桌面端 OpenAkita 更全 OpenAkita 具备完整全栈能力，Mona 专注后端核心
🔄 Agent 执行循环
核心循环模型 事件驱动状态机：TurnState 枚举定义 8 个状态（RESTORE→COMPACT→COMMAND→BUILD→RUN→SAVE→RESPOND→DONE），通过 _TRANSITIONS 转移表驱动 Ralph Wiggum 循环引擎：RalphLoop 实现"永不放弃"模式，StopHook 拦截退出尝试，最多 100 次迭代，每次从 MEMORY.md 加载状态 设计哲学不同 Mona 是严谨的状态机，流程清晰可追踪；OpenAkita 是"死磕到底"循环，强调任务完成率。Mona 更工程化，OpenAkita 更激进
迭代上限 max_iterations 可配置（默认来自 AgentDefaults），到达上限后返回 max_iterations stop_reason 默认 max_iterations=100，max_attempts=10（per-task），另有 TASK_BUDGET_DURATION 预算限制 OpenAkita 更高 OpenAkita 迭代上限更高且有多层预算控制；Mona 更保守，倾向于快速完成或快速失败
LLM 调用层 AgentRunner 是纯 LLM 循环引擎，不关心产品层逻辑；支持流式/非流式/progress-streaming 三种模式 LLM 调用封装在 Agent 类内部，30+ provider 支持，smart failover 自动切换 Mona 更解耦 Mona 将 LLM 调用与产品逻辑分离为独立 AgentRunner，可复用性更强；OpenAkita 集成度更高
🤝 多 Agent 协作
协作架构 SubagentManager 管理后台子任务；子 Agent 通过 MessageBus 注入结果（mid-turn injection），主 Agent 在同一 turn 内消费 AgentOrchestrator 中央协调器 + AgentFactory 工厂 + AgentInstancePool 实例池 + AgentMailbox 邮箱通信 OpenAkita 更成熟 OpenAkita 有完整的多 Agent 编排体系（工厂/池/邮箱/健康追踪），Mona 是轻量的主从模式
Agent 差异化 子 Agent 与主 Agent 共享相同工具集（通过 ToolLoader scope="subagent" 构建），仅系统提示不同 AgentProfile 定义身份/技能/工具/MCP/插件/记忆/权限 7 个维度的隔离配置，支持 INCLUSIVE/EXCLUSIVE/ALL 三种技能模式 OpenAkita 更灵活 OpenAkita 的 Agent 差异化能力远超 Mona，支持角色化分工（CEO/CTO/CFO 等）
委派深度 无显式深度限制，子 Agent 不可再委派（单层） MAX_DELEGATION_DEPTH = 5，支持多级嵌套委派 OpenAkita 更深 OpenAkita 支持递归委派，适合复杂组织架构场景
结果回传 子 Agent 通过 bus.publish_inbound() 发送 system 消息，主 Agent 的 pending_queue 消费（mid-turn injection），最多 3 条/轮，5 轮 子 Agent 通过 AgentMailbox 异步通信，DelegationResult 结构化返回（含 exit_reason/artifacts/tools_used） 各有侧重 Mona 的 mid-turn injection 更实时（流式场景友好），OpenAkita 的结构化结果更完整
🔧 工具系统
工具注册 ToolRegistry + ToolLoader 插件式加载，ToolContext 注入运行时依赖 工具分 handler（tools/handlers/）+ definition（tools/definitions/），89+ 内置工具，8 种插件类型 OpenAkita 更丰富 OpenAkita 工具数量和类型远多于 Mona，但 Mona 的插件加载机制更简洁
并发执行 支持 concurrent_tools=True，_partition_tool_batches 按 concurrency_safe 标记分批并行执行 工具执行在 Agent 内部串行处理（单 Agent 内），多 Agent 并行通过 Orchestrator 实现 Mona 更细粒度 Mona 在单 Agent 内支持工具级并发，OpenAkita 在 Agent 级并发
MCP 集成 内置 MCP 客户端（connect_mcp_servers），支持 stdio/HTTP/SSE 传输，懒加载连接 MCP 集成 + mcp_catalog 管理，支持按 profile 过滤 MCP 服务器 能力相当 两者都支持标准 MCP 协议，OpenAkita 多了 profile 级过滤
🧠 记忆与上下文管理
记忆存储 纯文件 I/O：MEMORY.md（长期事实）、SOUL.md（人格）、USER.md（用户偏好）、history.jsonl（历史） SQLite + SearchBackend（FTS5/向量搜索）：UnifiedStore 统一存储，SemanticMemory 结构化记忆，支持去重/过期/作用域隔离 OpenAkita 更强 OpenAkita 有数据库级存储和语义搜索，Mona 的文件方案更简单但缺乏查询能力
上下文压缩 Consolidator 基于 token 预算触发 LLM 摘要压缩；AutoCompact 空闲会话硬截断；_microcompact 旧工具结果摘要；_snip_history 滑动窗口 PromptCompiler 编译身份文件，PromptBuilder 分层组装；MDRM 关系图记忆（因果链/时间线/实体图）；3D 可视化 Mona 更精细 Mona 有 4 层压缩策略（LLM摘要/硬截断/微压缩/滑动窗口），token 治理更精细；OpenAkita 的关系图记忆更高级
后台记忆处理 Dream 两阶段处理器：Phase1 分析历史→Phase2 用 AgentRunner + read_file/edit_file 工具增量编辑记忆文件，支持 git blame 行龄标注 自进化引擎（evolution/）：每日自检修复、失败根因分析、自动技能生成 各有特色 Mona 的 Dream 更偏向记忆维护，OpenAkita 的自进化更偏向能力扩展
📝 提示词工程
系统提示构建 ContextBuilder 拼装：identity → bootstrap(AGENTS.md/SOUL.md/USER.md) → tool_contract → memory → skills → history → session_summary PromptCompiler 编译身份文件 → PromptBuilder 分层组装：Identity → Persona → Runtime → Session Rules → AGENTS.md → Catalogs → Memory → User 架构相似 两者都是分层组装，OpenAkita 多了 Persona 和 Catalogs 层，Mona 更扁平
技能系统 SkillsLoader 加载 SKILL.md，支持 YAML frontmatter 元数据，渐进式加载（summary→按需 read_file），always 标记常驻技能 技能市场 + AI 动态生成技能，3 种模式（ALL/INCLUSIVE/EXCLUSIVE），ESSENTIAL_SYSTEM_SKILLS 基础保障 OpenAkita 更丰富 OpenAkita 有技能市场和动态生成能力，Mona 的渐进式加载设计更节省 token
🛡️ 安全机制
安全层级 工作区限制（restrict_to_workspace）、SSRF 防护（不可绕过的硬边界）、文件状态追踪、沙箱执行（exec_session） 6 层沙箱：路径分区 → 确认门 → 命令拦截 → 文件快照 → 自保护 → OS 级沙箱（Linux bwrap / macOS seatbelt / Windows MIC） OpenAkita 更深 OpenAkita 的 6 层沙箱纵深防御远超 Mona，但 Mona 的 SSRF 防护更精细（含白名单机制）
权限控制 工具级 prepare_call 前置校验，workspace violation 重复检测升级提示 3 层权限模型 + AgentProfile permission_rules 注入 + 工具/技能/MCP 独立过滤 OpenAkita 更完善 OpenAkita 有细粒度的权限规则系统，Mona 依赖工具级校验
⚠️ 错误处理与容错
重试策略 Provider 级 chat_with_retry；空响应最多重试 2 次 + finalization retry；输出截断自动续写（length_recovery 最多 3 次） RalphLoop StopHook 拦截退出，max_attempts=10；_analyze_and_adapt 错误分析策略调整（TODO: 更智能分析） Mona 更精细 Mona 针对不同错误类型有专门处理（空响应/截断/SSRF/工作区违规），OpenAkita 的重试更粗暴但更执着
中断恢复 runtime_checkpoint 机制：工具执行期间持久化中间状态到 session metadata，/stop 后可恢复部分上下文 通过 MEMORY.md 持久化任务状态，每次迭代 fresh context 重新加载 Mona 更精确 Mona 的 checkpoint 粒度到消息级，OpenAkita 是文件级粗粒度恢复
上下文治理 5 步治理链：_drop_orphan_tool_results → _backfill_missing_tool_results → _microcompact → _apply_tool_result_budget → _snip_history PromptCompiler 检测编译过期自动重编译；token 预算由 MDRM 和 UnifiedStore 管理 Mona 更系统 Mona 有完整的上下文治理管线，确保 LLM 输入始终合法；OpenAkita 依赖编译器重编译
💬 人机交互
接入渠道 CLI、WebSocket（WebUI）、IM 通道（通过 MessageBus + channels 配置） 6 大 IM 平台（Telegram/飞书/企微/钉钉/QQ/OneBot）+ 桌面端 + Web + 移动端，扫码绑定 30 秒接入 OpenAkita 更广 OpenAkita 的渠道覆盖远超 Mona，尤其 IM 集成和移动端
流式输出 完整流式支持：on_stream 内容增量 + on_stream_end 分段标记 + emit_reasoning 思维链流式 + 文件编辑实时追踪 IM 流式推送、深度思考模式实时链式展示、WebUI 流式渲染 能力相当 两者都支持流式，Mona 的流式钩子更细粒度（文件编辑追踪）
中途消息注入 pending_queue 机制：会话活跃期间新消息路由到待处理队列，支持 mid-turn injection（最多 3 条/轮，5 轮） AgentMailbox 异步消息队列，drain_all 批量消费 Mona 更实时 Mona 的 mid-turn injection 允许在 LLM turn 中途注入，实时性更强
🤖 模型支持
Provider 抽象 LLMProvider 基类 + ProviderFactory 工厂 + ProviderSnapshot 运行时切换 30+ LLM provider 注册表，smart failover 自动切换 OpenAkita 更广 OpenAkita 支持更多 provider，Mona 的运行时切换机制更灵活
模型预设 ModelPresetConfig + model_presets 字典，支持运行时切换预设（含 provider/model/context_window 联动更新） preferred_endpoint + endpoint_policy（prefer/fallback），per-profile 端点配置 Mona 更灵活 Mona 的预设系统支持多维度联动切换，OpenAkita 的 per-profile 配置更实用
📊 可观测性
执行追踪 StateTraceEntry 记录每个状态的耗时和事件；AgentHookContext 暴露迭代级指标；turn_latency_ms 延迟追踪 12 种 trace span 类型，全链路 token 统计面板，Agent 仪表盘神经网络可视化 OpenAkita 更直观 OpenAkita 有可视化仪表盘，Mona 的追踪更偏日志/结构化数据
Hook 系统 AgentHook 生命周期钩子（before_iteration/on_stream/before_execute_tools/after_iteration/finalize_content），CompositeHook 错误隔离扇出 10 种插件生命周期钩子，8 种插件类型 各有侧重 Mona 的 Hook 更面向执行流程定制，OpenAkita 的 Hook 更面向插件生态扩展
