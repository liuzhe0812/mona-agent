Mona 收藏与记忆机制

v1.1 · 全阶段完成 Agent 记忆基础设施 2026-07-08

Mona 的「收藏」并不是一个独立的剪贴板，而是Agent 的跨源记忆层。 它把用户在浏览器、邮件、对话中表达过「关注意图」的内容沉淀下来， 供 Agent 在后续对话中召回，让 Mona 真正「记住」用户看过什么、收藏过什么、聊到过什么。

1. 定位与设计理念

传统剪贴板式收藏（Pocket、Karakeep 等）解决的是「把网页存下来以后看」的问题。 Mona 的 Hoard 解决的是另一个问题：

核心命题
让 Agent 在对话中能主动召回用户曾经关注过的内容，而不需要用户每次重新粘贴链接或描述背景。

与 Karakeep 的区别

维度Karakeep（独立应用）Mona Hoard（原生集成）
定位个人书签库Agent 记忆基础设施
触发用户手动收藏用户主动 + Agent 自动判断
召回用户搜索浏览Agent 对话中主动召回
关联标签/文件夹跨信息源 URL + 语义双关联
存储独立服务SQLite，与 Mona 同进程
检索单一关键词或向量双路径自适应（关键词 / Hybrid）

三个关键决策

  • 不索引浏览轨迹：只索引用户/Agent 主动收藏的内容，避免噪音淹没信号。
  • Agent 自动入库但降权：Agent 判断有价值即可入库，source_strength=0.8，用户可在 UI 删除。
  • 关联双路径：URL 精确匹配（始终启用）+ 语义相似度匹配（配置 Embedding 后启用）。

2. 三条信息源路径

Mona 的 Agent 在回答问题时，可以从三个独立的信息源获取上下文。这三条路径职责分离、互不污染：

📚

知识库（KB）

用户主动导入的 LLM Wiki 文档。
工具：kb_search
场景：查文档、查规范

📝

笔记（Notes）

Obsidian 风格的 Vault。
工具：notes_search
场景：查用户自己写的笔记

🧠

收藏记忆（Hoard）

跨源沉淀的 URL/片段。
工具：hoard_search
场景：「之前看过的」「邮件里提到的」

为什么不合并？
KB 是「权威资料」，Notes 是「用户产出」，Hoard 是「关注过的外部内容」—— 三者权威性、可信度、召回时机都不同。合并会让 Agent 难以判断引用时的语境。
三源检索对齐
KB、Notes、Hoard 三条路径现在统一采用双路径自适应设计： 无 Embedding 配置时用关键词检索，有配置时用 Hybrid 检索。 用户只需在全局配置一次 Embedding，三个信息源同时升级。

3. 收藏触发方式

用户主动收藏（source_strength = 1.0）

入口操作来源标记
浏览器收藏栏右键书签 → 「收藏到记忆」browser
邮件列表右键邮件 → 「收藏到记忆」email
管理面板手动添加（规划中）manual

Agent 自动收藏（source_strength = 0.8）

Agent 在对话中通过 hoard_capture 工具主动入库。判断标准：

  • 用户表达关注意图：「记一下」「收藏下」「这个有用」「回头要看」
  • Agent 判断某 URL/片段对未来对话有潜在价值
不触发的场景
用户随口提及的 URL、负面评价的内容、临时示例链接 —— 这些不应入库，否则会污染记忆。

4. 数据模型

每条 Hoard 项的字段如下：

字段类型说明
idstring唯一 ID，格式 hoard-{uuid}
urlstring?原始 URL（片段型收藏可为空）
titlestring标题（必填）
contentstring?原始内容（URL 抓取后或邮件正文）
summarystring?LLM 生成的摘要（约 300 字）
tagsstring[]LLM 生成的标签（3-5 个）
sourcestring来源：browser / email / note / chat / manual
source_refstring?来源引用 ID（如 email_id、note_id、URL 本身）
source_strengthfloat来源强度：用户=1.0，Agent=0.8
asset_pathstring?关联的本地资源路径（如截图）
created_atint创建时间戳
last_accessed_atint?最后访问时间（预留）

向量存储（Embedding 启用时）

当用户配置了 Embedding 模型后，每条 Hoard 项会额外生成向量并存储到 hoard_vectors 虚拟表：

字段说明
hoard_id对应 Hoard 项 ID（主键）
vectorEmbedding 向量（float 数组，维度由模型决定）

向量由 title + tags + summary + content（前 1000 字） 拼接后生成，使用 sqlite-vec 存储，与主表同库。

5. 入库流水线

当一条 Hoard 项被创建后，系统会立即返回 ID，然后在后台异步执行入库流水线。

1
写入 SQLite
立即返回 ID，前端不阻塞
2
抓取 URL
SSRF 校验 → 下载 → 去 HTML → 截断 2000 字
3
LLM 摘要
主模型生成 300 字摘要
4
LLM 标签
生成 3-5 个标签
5
生成向量
可选：Embedding 配置时启用
6
建立关联
URL 匹配 + 语义匹配（可选）
自适应流水线
Step 5（生成向量）和 Step 6 的语义匹配部分仅在 Embedding 配置启用时执行。 未配置时流水线跳过这两步，但 URL 抓取、LLM 摘要、LLM 标签、URL 关联照常进行。
容错设计
流水线每一步都是非致命的：URL 抓取失败只存标题，LLM 调用失败只跳过摘要/标签， 向量生成失败不影响关键词检索。部分数据也会被存储，保证基础可用。

SSRF 防护

所有 URL 抓取都经过 validate_url_target 校验，禁止访问内网地址（127.0.0.1、localhost、192.168.* 等），防止 Agent 被诱导访问内网服务。

6. 检索机制（双路径自适应）

Hoard 的检索代码会自动检测全局 tools.embedding 配置，选择对应路径：

🟡 路径 A：关键词检索（默认）

未配置 Embedding 模型时启用

  • 方式：SQLite LIKE 子串匹配
  • 评分：title × 3 + tags × 2 + summary × 2 + content × 1
  • 加权：× source_strength
  • 返回：mode=keyword
  • 优点：中文友好、零依赖、即时可用

🟢 路径 B：Hybrid 检索（升级）

配置 Embedding 模型后自动启用

  • Phase 1：LIKE 关键词检索（同路径 A）
  • Phase 2：sqlite-vec 向量检索（余弦相似度）
  • Phase 3：RRF 融合（K=60）重排
  • 返回：mode=hybrid 或 vector
  • 优点：语义召回、跨词表泛化
为什么不用 FTS5？
我们实测了 SQLite FTS5 的 trigram、unicode61、porter 三种 tokenizer， 对中文 2 字词（如「渲染」「前端」「架构」）全部返回 0 命中。中文分词需要 jieba 等外部分词器， 而 LIKE 子串匹配对中文天然友好，且无额外依赖。

关键词评分公式

score = (3 × title_hit + 2 × tags_hit + 2 × summary_hit + 1 × content_hit) × source_strength # 命中为 1，未命中为 0；source_strength: 用户=1.0, Agent=0.8

Hybrid RRF 融合公式

rrf_score = 1 / (60 + keyword_rank) + 1 / (60 + vector_rank) # 两路命中的项得到最高融合分；单路命中按其排名计分

三源检索对比

维度KB（知识库）Notes（笔记）Hoard（收藏）
存储Markdown 文件Markdown + FrontmatterSQLite + 向量库
无 EmbeddingLIKE 子串LIKE 子串LIKE 子串
有 EmbeddingHybrid (RRF)Hybrid (RRF)Hybrid (RRF)
评分字段title × 3, content × 1title × 3, tags × 2, content × 1title × 3, tags × 2, summary × 2, content × 1
来源加权无无有（source_strength）
双路径自适应✓✓✓

7. 跨源关联

Hoard 的关联机制采用双路径设计，与检索机制对齐：

路径 A：URL 精确匹配（始终启用）

当一条 Hoard 项带有 URL 时，系统会扫描所有已有 Hoard 项，查找相同 URL 的其他条目，建立双向关联。

用户收藏 URL
来自浏览器
Agent 收藏同 URL
来自邮件/对话
双向关联
写入 hoard_relations 表
召回时展示
related_sources 字段

路径 B：语义相似度匹配（Embedding 启用时）

配置 Embedding 后，入库流水线会额外执行语义关联构建：

  • 用当前项的文本（title + tags + summary + content）生成查询向量
  • 在 hoard_vectors 表中检索 Top-6 最相似的项
  • 相似度 ≥ 0.75 的项建立 related_type="semantic" 双向关联
  • 元数据中包含相似度分数，便于 UI 展示
双路径并存
URL 匹配和语义匹配互不替代，互为补充： URL 匹配捕获「同一内容不同来源」的硬关联，语义匹配捕获「相似主题不同内容」的软关联。 两种关联都写入同一张 hoard_relations 表，通过 related_type 区分。

关联表结构

字段说明
hoard_id当前 Hoard 项 ID
related_type关联方来源：browser/email/note/chat/hoard/semantic
related_id关联方的 source_ref 或 hoard_id
related_metaJSON 元数据（标题、URL、相似度分数等）

8. Agent 工具

Agent 通过两个工具与 Hoard 交互：

hoard_search（只读）

  • 用途：搜索用户在浏览器、邮件、笔记、对话中收藏过的内容
  • 触发场景：用户问「之前看过的」「上周聊到的」「邮件里提到的」
  • 检索方式：自动检测 Embedding 配置，无配置用关键词，有配置用 Hybrid
  • 返回：标题、URL、摘要、标签、来源、关联信息源、检索模式（keyword/hybrid/vector）
  • scope：core, subagent（可在子代理中调用）

hoard_capture（写入）

  • 用途：把 URL 或文本片段收藏到 Hoard
  • 触发场景：用户表达关注意图，或 Agent 判断内容有潜在价值
  • 默认参数：source="chat", source_strength=0.8
  • 入库流水线：自动检测 Embedding 配置，有则生成向量 + 语义关联，无则跳过
  • 非阻塞：流水线通过 asyncio.create_task 异步执行，不阻塞对话
  • scope：core（仅主 Agent，子代理不可写）
工具描述的设计
hoard_capture 的描述里明确写了「不要为用户随口提及、负面评价、临时示例的 URL 调用」， 通过 prompt 引导 Agent 做出合理的收藏判断。

9. 用户界面

右键菜单集成

在两个位置集成了「收藏到记忆」右键菜单项：

  • 浏览器收藏栏：右键任意书签 → 「收藏到记忆」→ 带 URL 入库
  • 邮件列表：右键任意邮件 → 「收藏到记忆」→ 带邮件正文（截断 2000 字）入库

管理面板

侧边栏新增「收藏」入口（Bookmark 图标），打开后是双栏布局：

  • 左栏（列表）：所有 Hoard 项，按时间倒序，显示来源徽章、标题、摘要预览、标签
  • 右栏（详情）：选中项的完整信息——URL、来源强度、收藏时间、标签、摘要、原始内容、关联信息源
  • 顶部：搜索框 + 来源过滤（全部/浏览器/邮件/笔记/对话/手动）
  • 右键菜单：打开链接、删除

实时同步

当用户在浏览器/邮件处右键收藏时，会派发 hoard-changed 事件，管理面板自动刷新列表，无需手动刷新。

10. 存储与端口架构

数据库位置

平台路径
Windows%APPDATA%/mona/hoard/hoard.sqlite3
macOS~/Library/Application Support/mona/hoard/hoard.sqlite3
Linux~/.local/share/mona/hoard/hoard.sqlite3

双端访问

Hoard 数据库同时被 Rust 侧和 Python 侧访问：

  • Rust 侧（Tauri 命令）：基础 CRUD，供前端直接调用
  • Python 侧（HoardManager）：直接 sqlite3 连接，供 Agent 工具和入库流水线使用
  • 向量库（sqlite-vec）：同一 SQLite 文件内的 hoard_vectors 虚拟表，仅 Python 侧访问

两端都实现了 _ensure_db 防御性建表，无论谁先访问都会自动创建表结构。

HTTP 路由

所有需要 POST body 的路由注册在 gateway aiohttp app（端口 17173）：
