1整体架构与角色分工

邮件功能由三层协作完成，每层职责清晰、相互独立。

前端（React + Zustand）

管理 UI 状态与用户交互。所有读操作优先走本地，写操作采用"本地优先 + 异步同步"策略，确保 UI 即时响应。

Rust 侧（Tauri 命令）

负责本地数据管理：SQLite 索引读写、.eml 文件落盘、.meta.json 维护、本地正文解析（mailparse）。所有 IMAP 网络请求也由 Rust 发起。

Python Gateway

仅负责 IMAP 协议交互：连接邮箱、FETCH 邮件头/正文、STORE 标志、MOVE 邮件。通过 asyncio.Lock 保证同账号 IMAP 操作串行，避免连接配额耗尽。

核心设计原则：本地优先（Local-First） 所有读操作走 SQLite 索引（毫秒级），所有写操作先落本地再异步同步 IMAP。参考 Foxmail / Mailspring 的设计：IMAP 同步在后台进行，永不阻塞 UI。

2存储分层模型

每封邮件在本地有三份存储，各司其职，构成 Foxmail 风格的文件 + 索引架构。

.eml 文件

邮件原始 RFC822 字节，是唯一真相源。包含完整头部、正文、附件。可被任何邮件客户端打开。

.meta.json

侧车文件，存储 RFC822 不含的状态：已读、星标、正文是否已拉取。保证 .eml 文件本身不被修改。

SQLite 索引

可重建的缓存索引。存储邮件头字段（主题、发件人、日期等）+ eml_path 指针。支持复合索引实现秒级查询。

为什么分三层？
  • .eml 是标准格式，可脱离应用独立打开，避免数据锁定
  • .meta.json 把用户状态与邮件原文分离，IMAP 重新同步不会覆盖本地状态
  • SQLite 仅做索引，体积小、查询快，损坏后可从 .eml 文件完全重建

SQLite 关键索引

索引用途查询场景
(account_id, folder, uid_int DESC)复合主索引列表分页、游标加载
(account_id, folder, uid)唯一约束UPSERT 去重
(account_id, folder, message_id)消息 ID 查找同步去重（发送副本 vs IMAP 版本）

3邮件收取流程

邮件收取分三种触发场景，底层共用同一个同步管道，但 UI 表现不同。

触发场景

场景UI 状态说明
用户点击「收取」按钮 syncing 全屏同步指示 主动同步当前文件夹，显示加载状态，禁用按钮
点击空文件夹（本地无邮件） backgroundSyncing 后台 spinner 列表立即显示空状态 + 小 spinner，同步完成后邮件 prepend，不阻塞
后台定时同步 / IMAP IDLE 推送 backgroundSyncing 静默 每 30 秒轮询 + IDLE 实时监听，新邮件自动入库并 prepend 到列表

同步管道（sync_folder_internal）

从前端点击到邮件落盘的完整链路
1
前端发起同步请求 携带账号信息、文件夹名、lastUid（本地已同步的最大 UID）。点击空文件夹时用 backgroundSyncing 标记，不设 syncing。
↓
2
Rust 调用 Gateway /email/sync POST 请求到 Python Gateway，Gateway 通过 asyncio.Lock 串行化同账号 IMAP 操作，避免连接配额问题。
↓
3
Gateway 连接 IMAP 增量拉取 UID SEARCH lastUid+1:* 获取新邮件 UID 列表。首次同步取最近 20 封，增量同步单次最多 50 封。仅拉取 BODY.PEEK[HEADER] + FLAGS，不下载正文。
↓
4
Gateway 返回邮件头 JSON 每封邮件包含 uid、subject、from、date、isRead、isStarred、rawBytes（HEADER 原始字节 base64 编码）。返回给 Rust。
↓
5
Rust 落盘 + 索引写入 对每封邮件：① base64 解码 rawBytes 写入 .eml 文件；② 写 .meta.json 侧车（isRead/isStarred/bodyFetched=false）；③ UPSERT 到 SQLite 索引表，保留用户已有的 isRead/isStarred 状态。
↓
6
去重处理 若本地存在相同 message_id 但不同 uid 的记录（如本地发送的 "L" 副本 vs IMAP 同步版本），删除旧版本及其 .eml/.meta.json，避免重复。
↓
7
更新 last_synced_uid 取本次同步中最大的 UID 写入 accounts 表，作为下次增量同步的起点。
↓
8
应用邮件规则（仅新邮件） 对本次新增的邮件匹配规则：标记已读/星标（本地+IMAP）、移动/删除（调 Gateway）。规则 MOVE 后不会递归触发规则。
↓
9
返回新邮件列表给前端 从 SQLite 查询仍留在当前文件夹的新邮件（规则可能 MOVE 走了部分），返回完整 EmailMessage 对象。
↓
10
前端增量 prepend + 通知 过滤掉已存在的 UID，将新邮件插入列表头部。非首次同步且检测到新邮件时弹右下角通知。刷新未读数。
422 错误的友好处理 企业邮箱（如腾讯企业邮）可能拒绝 SELECT 非收件箱文件夹，Gateway 捕获 "Mailbox select failed" 返回 422。前端识别 422 静默处理，不弹错误，仅显示空列表。

4邮件保存流程

邮件保存指将 IMAP 拉取的邮件落盘为本地文件并建立索引。所有写操作遵循固定顺序，保证一致性。

三层写入顺序（不可颠倒）

写操作的事务性顺序
1
写 .eml 文件（真相源） base64 解码 IMAP 返回的 rawBytes，写入 <app_data>/email/<account_id>/<folder>/<uid>.eml。同步时写 HEADER-only，fetch_body 时覆盖为完整 RFC822。
↓
2
写 .meta.json（侧车状态） 与 .eml 同目录，文件名 <uid>.meta.json。记录 isRead、isStarred、bodyFetched、messageId、emlMtime。用户状态变更时同步更新此文件。
↓
3
UPSERT SQLite 索引（可重建缓存） INSERT ... ON CONFLICT DO UPDATE。更新邮件头字段，但保留用户已设置的 isRead/isStarred（CASE WHEN 已为 1 则不覆盖）。eml_path 指向 .eml 文件相对路径。
为什么这个顺序？ 若先写 SQLite 再写 .eml，进程在中间崩溃会导致索引指向不存在的文件。先写 .eml 保证即使 SQLite 写失败，邮件数据仍在磁盘上，下次同步或重建索引时可恢复。

同步时的 UPSERT 策略

字段策略原因
subject / from / date 等头部始终覆盖IMAP 是权威源
is_read / is_starred本地为 1 则保留用户本地操作不应被 IMAP 状态覆盖
body_fetched本地为 1 则保留已拉取的正文不应回退
eml_path新值非空才覆盖避免空值清掉已有路径

5邮件列表加载流程

点击文件夹或切换账号时加载邮件列表。核心目标：秒级响应，无空白闪烁。

触发入口

统一由 EmailClientView 的 useEffect 监听 selectedAccountId + selectedFolder 变化触发 loadMessages，避免多处手动调用导致重复请求。

loadMessages 完整流程
1
不设 loading: true 本地 SQLite 查询通常 <10ms，设置 loading 会引起"加载中"闪烁。保留旧列表内容直到新数据就绪，实现无缝替换。
↓
2
SQLite 游标分页查询 SELECT ... ORDER BY uid_int DESC LIMIT 50。before_uid 为空时拉最新一页，非空时拉 uid_int < before_uid 的下一页。使用 uid_int 列（整数）替代 CAST(uid AS INTEGER)，走索引。
↓
3
从内存缓存恢复正文 SQLite 不存正文，但 bodyCache（Zustand store）有已解析过的正文。对每封邮件检查缓存 key，命中则填充 bodyText/bodyHtml，避免重新解析。
↓
4
防竞态检查 仅当当前 selectedAccountId 和 selectedFolder 仍与查询时一致才更新 state。避免用户快速切换文件夹时旧请求覆盖新结果。
↓
5
无缝替换列表 set messages + hasMore（等于 PAGE_SIZE 表示可能有更多）。UI 立即渲染新列表，无闪烁。
↓
6
空文件夹触发后台同步（仅本地为空时） 设置 backgroundSyncing: true，调 syncEmail 拉取邮件。仅当拉到新邮件时才重新 loadMessages（避免空文件夹无限递归）。同步完成或失败都置 backgroundSyncing: false。
性能数据
  • 本地有邮件的文件夹：<10ms 显示列表 秒开
  • 本地为空的文件夹：立即显示空状态 + 后台 spinner，同步完成后邮件自动出现
  • 滚动到底部自动加载下一页：游标分页，避免 OFFSET 越翻越慢

虚拟滚动

列表使用 @tanstack/react-virtual 虚拟滚动，仅渲染可见区域的邮件行（约 15-20 行），无论列表多少封邮件都保持流畅。每行高度 56px，overscan 8 行预渲染。

6正文加载流程

同步时只拉 HEADER，正文在用户点击邮件时按需加载。三层缓存策略保证秒级打开。

缓存层级

层级位置命中速度说明
L1 内存缓存Zustand bodyCache<1ms会话内有效，切换邮件/刷新列表时复用
L2 本地 .eml磁盘文件1-5msRust mailparse 本地解析，毫秒级
L3 IMAP 远程Gateway /email/fetch_body200-2000ms网络请求，拉完整 RFC822 并落盘
fetchBody 完整流程
1
检查 L1 内存缓存 key = uid:accountId:folder。命中且有内容则直接更新 messages/selectedMessage，立即返回。避免切换邮件时重复解析。
↓ 未命中
2
检查 bodyFetched 标志 若邮件对象已有 bodyFetched=true 且 bodyText 非空，直接返回（兼容旧数据）。
↓ 需要拉取
3
调用 Rust email_fetch_body 命令 前端调 Tauri invoke，传入 gatewayUrl、accountId、uid、mailbox。
↓
4
查 SQLite 获取 eml_path Rust 先从 SQLite 查询该邮件的 eml_path 字段，判断本地是否有 .eml 文件。
↓
5
本地有 .eml：Rust mailparse 解析（快路径） 读取 .eml 字节，用 mailparse crate 递归提取 text/plain 和 text/html。自动处理 MIME 多部分结构、字符集解码。纯本地操作，毫秒级，不走 Gateway HTTP。
↓ .eml 不存在或解析失败
6
本地无 .eml：调 Gateway IMAP FETCH（慢路径） POST /email/fetch_body，Gateway 连接 IMAP，UID FETCH BODY.PEEK[] 拉完整 RFC822。返回 rawBytes（base64）+ 解析后的 bodyText/bodyHtml。
↓
7
落盘 .eml + 更新索引 若 Gateway 返回 rawBytes，base64 解码后写入 .eml 文件。更新 SQLite：eml_path + body_fetched=1。更新 .meta.json：body_fetched=true。下次再点击此邮件即走快路径。
↓
8
写入 L1 缓存 + 更新 UI 前端将 bodyText/bodyHtml 写入 bodyCache，更新 messages 和 selectedMessage。正文截断到 50000 字符防止超大邮件卡死渲染。
为什么同步时不拉正文？
  • 一封邮件正文可能几 MB，50 封同步会拉上百 MB，同步超时严重
  • 大部分邮件用户不会点开，按需拉取节省带宽和存储
  • 点开过的邮件落盘 .eml，二次打开纯本地毫秒级
失败处理 fetchBody 失败时记录 bodyError 到邮件对象，UI 显示错误提示而非永远 loading。用户可重新点击邮件触发重试。

7已读状态变更流程

已读/星标状态变更采用"本地优先 + 异步同步"模式，确保 UI 即时响应且状态不丢失。

设计背景

早期版本直接调 IMAP STORE 设置标志，存在两个问题：① 网络延迟导致 UI 卡顿；② 企业邮箱拒绝非 INBOX 文件夹的 STORE 操作，导致已读状态下次打开又变回未读。本地优先模式彻底解决这两个问题。

toggleRead 完整流程
1
乐观更新 UI（立即） 前端立即反转 messages 和 selectedMessage 中的 isRead 字段，UI 瞬间响应，无任何等待。未读数同步更新。
↓
2
调用 Rust email_mark_read 前端调 Tauri invoke，传入 account_id、uid、mailbox、add（true=标记已读，false=标记未读）。
↓
3
本地优先：更新 SQLite（立即持久化） UPDATE messages SET is_read = ? WHERE uid=? AND account_id=? AND folder=?。即使 IMAP 同步失败，本地状态也已持久化，下次打开仍是已读。
↓
4
同步更新 .meta.json 读取侧车文件，更新 is_read 字段，写回磁盘。保证 .eml 重建索引时状态不丢失。
↓
5
异步同步 IMAP（失败不影响本地） POST /email/set_flag 到 Gateway，Gateway 调 IMAP UID STORE +FLAGS/-FLAGS \Seen。10 秒超时。失败仅记日志，不返回错误，不回滚本地状态。
↓
6
刷新未读数 从本地 SQLite 重新统计各文件夹未读数，更新文件夹树和托盘图标。
解决了什么问题
  • UI 即时响应：乐观更新，不等任何网络请求
  • 状态不丢失：SQLite + .meta.json 双写，即使 IMAP 失败也持久
  • 企业邮箱兼容：IMAP STORE 失败不报错，本地状态独立于服务器
  • 最终一致：下次 IMAP 同步时，服务器已读状态会自然对齐（或保持差异，不影响使用）

星标状态（toggleStarred）

星标状态变更与已读完全相同的流程，仅 SQLite 字段从 is_read 改为 is_starred，IMAP 标志从 \Seen 改为 \Flagged。同样采用本地优先 + 异步同步模式。

失败回滚策略

阶段失败处理
乐观更新后、Rust 调用失败回滚 UI 状态，恢复原 isRead 值，显示错误
SQLite 写入失败返回错误，前端回滚 UI
IMAP 同步失败仅记日志，不回滚，本地状态保持。下次同步自然对齐

8性能与一致性要点

关键性能优化

优化点措施效果
EmailState conn() 初始化AtomicBool 控制 schema 只初始化一次每次连接从 50-200ms 降至 1-5ms
uid_int 整数列 + 复合索引替代 CAST(uid AS INTEGER)分页查询走索引，避免全表扫描
正文本地解析Rust mailparse 直接读 .eml避开 Gateway HTTP 往返，毫秒级
同步仅拉 HEADERBODY.PEEK[HEADER]同步 50 封 <2 秒，正文按需拉取
虚拟滚动@tanstack/react-virtual万封邮件列表流畅滚动
游标分页uid_int < before_uid 替代 OFFSET翻页性能恒定，不随页数增加变慢
乐观更新UI 先反转，后端异步处理已读/星标切换零延迟

一致性保障

  • 写顺序固定：.eml → .meta.json → SQLite，崩溃可恢复
  • UPSERT 保留用户状态：同步不覆盖本地 isRead/isStarred/bodyFetched
  • 防竞态检查：异步操作完成后校验 selectedAccountId/selectedFolder 是否仍一致
  • message_id 去重：发送副本与 IMAP 版本按 message_id 合并，避免重复
  • 422 友好处理：企业邮箱文件夹限制静默处理，不弹错误

已知限制

当前限制与权衡
  • 非 INBOX 文件夹首次访问需后台同步，空文件夹显示 spinner（已优化为不阻塞）
  • 已读状态在离线时仅保存在本地，联网后异步同步，短期内服务器状态可能不一致
  • .eml 文件 HEADER-only 状态下无法解析正文，需 fetch_body 拉完整 RFC822 覆盖
  • 多账号并行同步受 IMAP 连接配额限制，默认串行化同账号操作
