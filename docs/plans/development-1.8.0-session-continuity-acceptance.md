## 1. 本轮解决的用户场景

原生线程已不存在时，用户应当在原开发任务中继续，而不是丢弃原对话、创建另一份项目或自动重放已经执行过的指令。

同时，网络超时、认证失败、项目配置错误以及结果未知都不能被当成“原线程不存在”。这些情况要保留实际状态，不擅自重建执行任务。

本轮区分两条路径：

1. **Codex 明确返回历史不存在**：只在当前产品会话没有未结束轮次时，建立新的原生绑定，并携带 full 模式的有界交接摘要。
2. **用户主动重新连接**：Codex、Claude Code、CodeBuddy 使用同一个产品操作；只有当前轮次已经确认结束才能执行。它只准备新的连接与交接，不发送开发指令。SDK 没有提供可靠的历史失效分类时，不冒充自动识别成功。

## 3. 执行与持久化变更

### 3.1 请求级错误分类

`executors/rpc.py` 为当前请求提供私有错误分类回调，仅在匹配的请求 ID 上执行；回调随请求结束移除。

原始供应商错误文本和数据不会进入产品异常、对话或持久化。上层只收到经过筛选的错误类别。

### 3.2 原绑定和交接的原子保存

`DevelopmentStore.activate_binding` 在同一事务内完成：

- 会话 revision 检查；
- 确认没有任何未结束轮次，而不是只检查 UI 最近一页记录；
- 验证同一个项目、执行者与只读权限；
- 保留旧绑定身份和历史，将其标记 stale；
- 激活新绑定，并记录 replacesBindingId / replacementReason；
- 保存待派发的 full 交接；
- 保存模型选择；
- 写入可追踪的续接事件。

旧绑定不会被覆盖成另一个原生 ID；交接未确认时不会被新记录覆盖。事务失败时，原会话、绑定与交接保持不变，并释放此次尚未执行任务的新原生连接。

### 3.3 不自动重跑

建立连接不等于发送请求。用户主动续接后，交接处于 pending，直到下一条真实请求被执行者接受才消费。

相同原绑定的续接请求丢失 HTTP 回执时，重复请求观察同一个已建立的后继绑定，不继续创建新的后继。

存在 running、waiting_user、interrupting、unknown、recovering 等非终态时禁止替代当前运行，但不阻止用户在同一项目中使用其他独立会话。

### 3.4 查询能力与恢复语义

新增明确的 `turnHistory` 能力，与 `resume` 分开。

- Codex 适配器具有读取指定原生轮次的实现。
- 当前 SDK 入口没有相应精确轮次查询接口时，返回不支持，不启动新 Worker 来伪装恢复，更不重发旧请求。
- 普通断线后恢复同一个已知原生会话、明确历史失效后的替代绑定，以及核对未知轮次结果，是三个不同操作。

## 4. 前端与 API

新增受现有本地令牌保护的：

`POST /api/development/sessions/{session_id}/reconnect`

请求携带当前 session revision 和原 binding ID；客户端不指定原生线程、路径、命令、权限或交接正文。

快照只增加安全的绑定摘要，不暴露交接正文或原生历史配置。

`DevelopmentContinuity` 使用现有 Dialog / Button 和语义样式：

- 用户明确确认“保留当前任务并重新连接”；
- 显示不会重发旧任务、不会修改文件的操作范围；
- 保留已捕获的原目标，回执未知时按原目标核对；
- 不清空主输入草稿；
- 当前任务执行中或状态未知时，不显示可用的替代连接操作；
- 发生替代后说明使用交接摘要，而非宣称恢复了原生内部状态。

未知轮次的“核对原任务”入口按实际 turnHistory 能力显示。没有能力时明确提示边界，不提供一个必然失败的假恢复按钮。
