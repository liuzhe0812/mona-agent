# Mona 上下文压缩优化方案与执行计划

日期：2026-09-11  
状态：核心实现已完成；64K/32K 性能试用尚未执行。  
目标：长任务能接着做、长会话不会无提示地丢内容，并在有实测收益时减少等待和调用成本。

## 1. 决策摘要

先修复摘要连续性和预算一致性，再提供独立的提前压缩阈值。复用现有会话、摘要、模型目录和运行状态组件，不另建上下文管理平台。

必须做的三件事：

1. 模型窗口在启动、切换、压缩、发送和显示之间一致。
2. 压缩生成“能继续任务的交接摘要”，成功后再替换旧上下文；本轮立即使用新摘要。
3. 区分提前整理阈值和模型安全预算，超限时有明确处理，压缩过程可见。

64K 触发、32K 目标仅作为大窗口模型的试用组合，不直接成为所有模型的默认值。闲置自动压缩、轮中完整语义压缩、独立压缩模型等暂不做。

## 2. 当前事实与需要纠正的判断

依据当前工作树核查，不等同于已运行桌面进程的状态。

| 当前机制 | 业务影响 | 判断 |
|---|---|---|
| 发送前检查历史，结束后安排后台整理；超过回放数量也会整理 | 不只是等 Token 用完；120 条包括工具交互，不等于 120 轮对话 | 保留现有入口，不再增加定时调度器 |
| 超过可用输入预算才压缩，目标为预算的 50% | 大窗口允许更多历史，但也可能增加首字等待和输入费用 | 阈值与容量应分开，具体阈值需要验证 |
| 摘要按旧消息片段生成，保存时覆盖 `_last_summary` | 连续压缩可能失去更早的约束、决策和未完成事项 | 高优先级修复 |
| `_state_compact` 先读取摘要，`_state_build` 后压缩 | 本轮可能删掉旧历史，却仍携带旧摘要；新摘要到下一轮才生效 | 高优先级修复 |
| 当前摘要提示词偏向用户事实、偏好和事件 | 未要求完整保留当前任务进展、关键路径、失败尝试及下一步 | 改进会话交接摘要，不扩展用户画像系统 |
| 摘要失败后仍推进整理游标；原始归档有长度截断 | “保存了片段”不能证明“被移出内容全部可恢复” | 失败不得当作成功压缩 |
| Runner 每次请求前已有 `_snip_history` 预算处理 | 已有轮中防护，但主要是裁剪；恢复最近用户轮次时允许超过预算 | 不能把现状说成完全没有轮中检查，也不能称其严格防超限 |
| 新目录解析接入了 provider snapshot 与设置返回 | `AgentLoop.from_config` 仍读取预设原值，fallback 最小窗口与 UI 主模型窗口也需核对 | 前次修复尚需端到端验收，不能只凭解析函数返回 1M 判定完成 |

此前约 46.8 秒是整轮耗时，不是已经分解出的首字等待时间。仅凭该记录，不能把全部耗时归因于 42.5K 输入，也不能承诺压缩后一定按比例变快。

## 3. 从 Codex 借鉴的最小范围

本地 Codex 源码区分模型窗口与自动压缩阈值；普通总量模式默认阈值不超过模型窗口的 90%，支持轮前检查、模型降档处理以及压缩生命周期。它并非默认所有任务在 64K 压缩。

远端 V2 的约 64K 是压缩后保留消息的预算，不是全产品统一的压缩触发阈值；本地摘要路径则有不同的保留策略。不能直接复制数字并推断相同收益。

Mona 借鉴：独立阈值、连贯摘要、成功后提交、可见状态、实际请求验证。暂不复制远端专用压缩协议、多策略切换、模型兼容哈希和新窗口调度框架。

## 4. 优化内容、收益和边界

### A. 统一有效预算（必做，工作量小至中）

价值：避免显示 1M、实际仍按 65K 整理，或主模型可用而备用模型接不住上下文。

- 复用 `resolve_model_context_window`，统一启动与运行时刷新；检查显式调用参数、独立预设、伙伴 Agent 和 fallback 链入口。
- 同一供应商、精确模型 ID 的有效目录值优先；未知值才使用配置回退。
- 跨供应商模型族推断仅是回退估计，不能当作该接入点的实测能力。现有去版本后缀和跨目录匹配需限制在明确支持的映射；不能识别时如实回退，不猜更大窗口。
- 继续使用 fallback 链最小窗口作为安全预算。设置 API 返回有效值；前端占用环按同一有效值计算，限制来源只在 hover 说明，不增加新的设置页面。
- 目录更新不应在每条消息上同步请求网络；复用缓存，并在已有刷新入口更新。

验收：配置原值为 65,536、测试目录窗口为 1M 时，新建运行时、切换后运行时、压缩器、实际请求预算和 UI 分母一致；小窗口 fallback 生效时各端也一致。未知模型与目录暂不可用仍可解释地回退。

### B. 保证压缩前后任务连续（必做，工作量中）

价值：用户不用重复要求；比进一步降低触发阈值更优先。

- 压缩输入为“上一份有效摘要 + 本次移出的完整旧轮次”。连续多批压缩时，每一批都以上一批已生成摘要为基础。
- 片段超过摘要请求预算时，按完整轮次分批并复用现有轮数上限；整理游标只能覆盖实际处理过的消息。禁止先截断摘要输入，再把未读部分一起标为已整理。
- 交接摘要必须保留：当前目标与未完成请求、用户约束和纠正、已完成与未完成工作、关键结论及依据、必要文件/产物引用、已失败尝试、下一步。只保存继续任务需要的信息，不把临时运行细节写进用户画像或长期偏好。
- 复用会话 `_last_summary`，明确摘要用途和长度限制；建议初始上限 8,000 字符。超限需重新收敛或判失败，不静默截掉尾部关键内容。
- 不沿用“无值得记忆的事实就输出 `(nothing)`”作为有效任务交接。空摘要、错误文本和未完成响应均视为失败。
- 在现有会话锁内，先得到并验证摘要，再一起保存摘要和整理游标；若保存失败则恢复内存中的旧状态。成功后重新取得摘要与历史，本轮发送立即使用。
- 后台压缩只能提交其读取时对应的历史范围，用户新消息或取消不能被覆盖。复用现有锁与保存逻辑，只有测试证实存在竞态才补最小版本核对。
- 软阈值压缩失败：保留原摘要、游标和历史，只要实际输入仍在安全预算内就继续；本轮不循环重试压缩。超过硬预算则进入 C 的超限处理。
- 压缩调用必须有有限等待时间并支持取消，优先复用已有模型请求超时和重试策略，避免在发送前无限等待；不新增独立重试调度器。

验收：连续压缩两次后，第一次的关键约束仍在最新摘要；本轮请求已含新摘要；摘要错误、保存失败和后台并发均不能无声移除历史。保留当前用户请求及工具调用/返回的配对关系。

### C. 独立压缩阈值与发送前安全检查（必做基础能力，性能参数后验）

价值：给大窗口模型留出可调的成本和速度控制，同时保护长工具链。

只新增一个主要配置：`auto_compact_token_limit`（JSON 为 `autoCompactTokenLimit`），放入 `mona/config/schema.py`，默认 `null`；暂不增加模型级策略表。复用现有 `consolidation_ratio=0.5`。

现有 `context_block_limit` 如被显式设置，仍作为更小的请求输入限制，与模型安全预算取小值；不能替代软压缩阈值，也不能覆盖成大于模型容量的预算。

预算定义：

- `W`：统一解析后的有效上下文窗口，已计入 fallback 限制。
- `H = W - 最大输出额度 - 既有安全余量`：完整请求的安全输入预算。
- `T = min(显式 auto_compact_token_limit 或 floor(W × 0.9), H)`：提前压缩触发线。
- `G = floor(T × consolidation_ratio)`：压缩后的目标输入量。

所有比较均包含系统提示、工具定义、摘要、历史、新用户消息和必要媒体开销；不是只数聊天正文。实际新输入应替代当前 `[token-probe]` 占位的决策依据。

执行规则：

1. 轮前或轮后触发整理时，按完整旧轮次从早到晚压缩，保留最新用户任务轮次。
2. 不强制“留 8–12 条”：一轮工具链可能超过该数量。先保证完整轮次，再按预算决定保留多少。
3. 固定提示和当前任务已超过 `G` 时，允许达不到软目标；记录原因并停止反复摘要，只要能满足 `H` 即可继续。
4. 长工具链继续复用每次请求前的检查，首期只强化硬预算，达到软阈值不在轮中自动重建 system prompt。
5. 超限工具结果使用既有全文落盘与恢复引用机制；不可凭内容猜测截断。裁剪或替换后再次计算完整请求。
6. 仍超过 `H` 且没有合法收缩办法时，保存已完成进度并给出明确原因，不发送已知超限请求，不把中断报告为完成。
7. 切到更小窗口时先解析新预算并做轮前检查；复用现有摘要调用，只有真实兼容问题才考虑单独压缩模型。

试用值：对目录识别到的大窗口模型设置 `T=64,000`、`G≈32,000`。该组合不覆盖模型的 `W`，不把“上下文占用率”分母改成 64K。通过第 6 节收益检查后再决定是否作为产品默认值。

### D. 等待状态与最小诊断记录（随上述改动交付，工作量小）

价值：用户知道正在整理，而不是误以为消息没发出；开发者能区分压缩慢与模型首字慢。

- 复用“进行中”条，只在压缩实际运行期间显示“正在整理上下文”；完成、失败或取消后恢复正确状态。后台整理不把已完成会话重新标为对话生成中。
- 复用现有日志记录压缩原因、前后估算量、耗时、成功/失败及预算来源；分别记录发送到首个模型事件、首段正文与整轮耗时。不记录对话正文、完整请求或凭据。
- 最后一次服务端输入用量用于诊断估算偏差，禁止拿累计计费 Token 直接判断当前上下文。跨模型、跨压缩后的旧用量不复用。
- 暂不做自动误差校准算法、性能仪表盘或新的追踪系统。

## 5. 执行批次

每批独立验收，必要检查通过即停止扩展。复杂整合由主 Agent 负责，边界明确的测试用例或文档核对可交给 Luna。

| 批次 | 工作与主要文件 | 完成标准 | 依赖 |
|---|---|---|---|
| 0. 固定基线 | 确认工作树与运行中版本；梳理 `providers/context_window.py`、`factory.py`、`loop.py`、`settings_api.py` 入口；保留现有修改 | 明确已有功能与未闭合路径，准备最小测试输入 | 无 |
| 1. 预算一致 | A；补启动与刷新契约；前端继续消费后端有效值；窗口来源必要时进入现有响应 | 大小模型切换、启动、fallback、未知目录验证一致 | 0 |
| 2. 摘要正确 | B；`agent/memory.py`、`loop.py`、会话摘要提示词；必要时触及 `session/manager.py`；加入 D 的整理状态 | 两次压缩连续、当轮生效、失败不推进、并发不覆盖 | 1 |
| 3. 阈值与硬防护 | C；配置 schema、预算计算、Runner 最终检查；补 D 的耗时记录 | 新输入计入预算，无合法边界时不死循环，不发已知超限请求 | 2 |
| 4. 小范围试用与交付 | 对大窗口模型试用 64K/32K，完成收益检查；更新稳定架构说明 | 有记录支持启用或不启用新默认值，明确适用范围和回退方式 | 3 |

预估总工作量：约 3–5 个开发工作日，仅作排期参考；若轮中完整语义压缩成为必要条件，另立任务，不塞入本次范围。

## 6. 验证与采用门槛

### 正确性验收

| 场景 | 必须观察的真实行为 |
|---|---|
| 首轮启动与连续切换大小模型 | 实际传入 Runner、压缩器及 API 的预算一致 |
| 两次连续压缩 | 旧约束、已完成工作和未完成请求均可在新摘要与后续请求中恢复 |
| 用户发送导致轮前压缩 | 发送请求包含刚生成的摘要、新用户输入；不会滞后一轮 |
| 压缩服务报错或摘要为空 | 整理游标、旧摘要和原始历史不变，无假成功 |
| 后台整理与发送/停止重叠 | 新消息和检查点不会被旧快照覆盖 |
| 当前一轮或单个工具结果很大 | 工具配对完整、外置内容可恢复；仍超限则明确暂停 |
| 小窗口 fallback | 不用主模型大窗口掩盖备用模型限制 |
| 占用环与整理提示 | 无模型输出时仍显示进行中；实际整理时才显示整理状态 |

优先扩展现有 `test_consolidator.py`、`test_loop_consolidation_tokens.py`、`test_runner_governance.py`、`test_runtime_refresh.py`、`test_runner_fallback.py`、设置契约与输入区测试。断言真实持久化和请求内容，不只断言 mock 被调用。

Python 运行改动文件的 `ruff check` 及相关测试；前端协议或状态有变化时运行相关 Vitest 与 TypeScript 检查。无需 Rust 全量构建、Office 全量测试或部署。

### 提前压缩的收益检查

使用脱敏固定场景：短问答、多轮需求讨论、长工具结果任务。对照相同模型、推理强度与相同输入，在低于触发线的短场景以及超过 64K 的长场景各做少量配对重复，至少 3 组，记录冷/热缓存条件。

比较端到端等待、首段正文时间、输入量、摘要调用次数与额外输入/输出成本，以及预先列出的关键事实是否保留。压缩当轮和后续至少 3 轮一起计入成本，不能只展示压缩后单轮变快。

采用 64K 默认值的门槛：关键事实验收无新增丢失；短场景不新增压缩；长场景在含压缩开销的总成本或等待上有重复可见的改善，另一项无明显恶化。少量样本仅用于初步选择，不宣称统计显著或保证固定提速百分比。收益不稳定就保留可配置能力，不强推该默认值。

本方案未执行上述试用，也不把以前一次慢请求当作性能对照结果。

## 7. 明确暂不做

| 暂缓项 | 原因与重新考虑条件 |
|---|---|
| 默认开启闲置 30–60 分钟自动压缩 | 尚未证明收益，会额外调用模型，也可能清理用户稍后还要继续的细节 |
| 轮中完整语义压缩与新窗口协议 | 会触及 system prompt 稳定性、工具恢复和流式生命周期；先补现有硬防护 |
| 给所有模型固定 64K | 能力、缓存和价格不同，先试用 |
| 专用廉价压缩模型与失败自动切模型 | 增加供应商配置和摘要质量变量；当前模型压缩仍够用时不引入 |
| 多层摘要、向量库、自动召回全套历史 | 优先用一份累积交接摘要解决已确认缺陷 |
| 复制 Codex 远端压缩与兼容哈希 | 依赖特定模型协议，Mona 多供应商场景暂不需要 |
| 批量重压缩历史会话 | 增加成本和不可逆的信息损失，按新请求渐进生效即可 |

## 8. 回退与交付范围

- 提前压缩不理想时，把 `autoCompactTokenLimit` 恢复为 `null`，回到模型相关阈值；若需完全恢复旧触发时机，可设到安全预算，由后端钳制。
- 预算一致性、摘要合并和失败不提交属于正确性修复，不随性能参数回退。
- 摘要字段保持旧会话可读；旧摘要作为第一次合并的输入，不批量改写用户历史。
- 不改变本轮 system prompt；不直接修改生产配置、重启服务或发布安装包。
- 实施完成后更新 `docs/architecture/engineering-boundaries.md` 中稳定规则；临时验收记录留在本计划。发布时必须注明实际运行版本和启用参数。
