## 一、总体架构

### 1.1 复用 PPT 模块的成熟模式

三份调研确认了一个关键事实:**PPT 模块的"前端 newChat → 后端 session.metadata → DocumentAgentLoop 委派 → 文件系统约定 project_path → 轮询展示产物"模式完全可复用**。视频和流程图只需:

1. 前端调 `newChat(agentKind)` 创建 session(已就绪)
2. 后端 `DocumentAgentLoop` 按 profile 委派(已就绪)
3. agent 在 workspace 下创建 `<kind>_projects/<name>/` 目录
4. 前端轮询文件系统展示产物

**不需要改动**的核心组件:`loop.py` 委派逻辑、`websocket.py` session 创建、`mona-client.ts` WS 协议、`ThreadMessages`/`AgentActivityCluster` 聊天 UI。

### 1.2 新增的后端 HTTP 路由

仿 PPT 的 `/api/ppt/*` 模式,新增两组路由:

| 路由组 | 端口 | 用途 |
|--------|------|------|
| `/api/video/*` | gateway(17173) | 视频项目管理、产物读取、渲染状态 |
| `/api/flowchart/*` | gateway(17173) | 流程图项目管理、产物读取、draw.io 静态文件 |

## 二、Phase 3:视频模块实际功能

### 2.1 依赖管理(质量优先方案)

Hyperframes 需要 **Node.js 22+ + FFmpeg + Chrome**。按"延迟下载 + 首次提示"策略:

#### 2.1.1 运行时检测与下载

后端新增 `mona/api/video_runtime.py`:

```python
# 检测顺序:系统已装 > 用户数据目录缓存 > 提示下载
# 三者均无时,前端弹窗提示

class VideoRuntime:
    """管理视频渲染所需的三个运行时依赖"""

    def check_all(self) -> dict:
        """检测 Node.js / FFmpeg / Chrome 是否可用"""
        return {
            "node": self._check_node(),      # node --version >= 22
            "ffmpeg": self._check_ffmpeg(),   # ffmpeg -version
            "chrome": self._check_chrome(),   # hyperframes browser path
        }

    def ensure_runtime(self, component: str) -> dict:
        """下载指定组件到 <userData>/runtime/<component>/"""
        # Node.js: 下载 node-v22.x.x-win-x64.zip,解压到 runtime/node/
        # FFmpeg: 下载 ffmpeg-win64-gpl.zip,解压到 runtime/ffmpeg/
        # Chrome: 调用 npx hyperframes browser ensure(自动下载到 npx 缓存)
```

#### 2.1.2 前端提示流程

```
用户首次创建视频项目
  → 后端 /api/video/runtime-check 检测四个依赖(Node / FFmpeg / Chrome / hyperframes npm)
  → 若全部就绪:直接进入生成流程
  → 若有缺失:前端弹出依赖管理对话框
     "视频制作需要以下运行时环境:
      ✓ Node.js 22+(已检测到 v22.5.1)
      ✓ hyperframes CLI(已检测到 v0.7.65)
      ✗ FFmpeg(未检测到,下载约 80MB / 解压 100MB)
      ✗ Chrome Headless Shell(未检测到,下载约 108MB / 解压 280MB)
      [一键下载缺失组件] [稍后再说]"
     → 用户确认后,后端异步下载到 <userData>/runtime/,前端显示进度条
     → 下载完成后自动进入生成流程
```

#### 2.1.3 下载源与校验

| 组件 | 下载源 | 下载大小 | 解压后 | 校验 |
|------|--------|---------|--------|------|
| Node.js 22 | `https://nodejs.org/dist/v22.x.x/node-v22.x.x-win-x64.zip` | ~30 MB | ~70 MB | SHA256 |
| FFmpeg | `https://github.com/BtbN/FFmpeg-Builds/releases/download/latest/ffmpeg-master-latest-win64-gpl.zip` | ~80 MB | ~100 MB | SHA256 |
| Chrome Headless Shell | `npx hyperframes browser ensure`(走 Chrome for Testing CDN) | ~108 MB | ~280 MB | hyperframes 自校验 |
| hyperframes npm 依赖 | `npx hyperframes <cmd>` 首次执行自动拉取 | ~95 MB(剔除 onnxruntime) | ~95 MB | npm 自校验 |

macOS/Linux 下载源按平台区分,Windows 优先(项目主要支持 Windows)。

**关键说明**:hyperframes 的 npm 依赖默认不在安装包内,首次执行 `npx hyperframes` 时自动写入 `~/.npm/_npx/`。其中 `onnxruntime-node`(258MB)占依赖体积 73%,提供节拍检测 + 背景移除两个高级功能。详见 2.7 节打包体积评估。

### 2.2 Hyperframes CLI 集成

#### 2.2.1 命令封装

后端新增 `mona/skills/mona-video/scripts/hyperframes_cli.py`,封装 CLI 调用:

```python
class HyperframesCLI:
    """Hyperframes CLI 封装,处理环境变量和路径"""

    def __init__(self, project_path: Path, runtime: VideoRuntime):
        self.project = project_path
        self.runtime = runtime
        # 构建环境变量,确保 CLI 能找到 node/ffmpeg/chrome
        self.env = {
            "PATH": f"{runtime.node_bin};{runtime.ffmpeg_bin};{os.environ['PATH']}",
            "NODE_PATH": str(runtime.node_lib),
        }

    async def init_project(self, resolution: str = "landscape") -> dict:
        """npx hyperframes init <name> --example blank --resolution <r> --non-interactive"""

    async def lint(self) -> dict:
        """npx hyperframes lint --json,返回结构化校验结果"""

    async def validate(self) -> dict:
        """npx hyperframes validate --json,检查对比度等"""

    async def inspect(self, samples: int = 15) -> dict:
        """npx hyperframes inspect --samples <n> --json,检查文字越界"""

    async def render(self, output: str, quality: str = "standard", fps: int = 30) -> dict:
        """npx hyperframes render --output <path> --quality <q> --fps <f> --strict"""

    async def preview_server(self, port: int) -> asyncio.subprocess.Process:
        """npx hyperframes preview --port <p>,返回长驻进程供 WebView2 加载"""
```

#### 2.2.2 渲染全流程(质量优先)

agent 完成场景编写后,后端按以下顺序执行**完整质量门禁**:

```
1. lint        — 结构校验(composition 属性、时间线注册、轨道冲突)
2. validate    — 对比度/可访问性检查
3. inspect     — 抽样 15 帧检查文字越界
4. render      --strict  — 严格模式渲染,任何 lint 错误则停止
```

每一步结果通过 WebSocket 推送到前端,实时显示质量检查进度。

**质量门禁校验项明细**:

| 步骤 | 校验项 | 失败处理 |
|------|--------|---------|
| lint | 根 composition 四要素(data-composition-id/width/height/duration) | agent 修复,重跑 lint |
| lint | clip 元素四要素(class/data-start/data-duration/data-track-index) | agent 修复,重跑 lint |
| lint | 同 track-index 时间区间不重叠 | agent 调整时间,重跑 lint |
| lint | 禁用框架(React/Vue/Svelte 的 import/require) | agent 改写为原生 JS |
| lint | GSAP timeline 注册到 `window.__timelines[id]` | agent 补注册代码 |
| validate | 文字与背景对比度 WCAG AA ≥ 4.5:1 | agent 调整颜色,重跑 validate |
| validate | 字体大小、行高、间距的可读性 | agent 调整样式 |
| inspect | 抽样 15 帧的文字越界(clip-path/text-overflow) | agent 修 clip 边界 |
| inspect | 元素溢出 composition 边界 | agent 调整布局 |
| inspect | 帧间错位(动画 keyframe 异常) | agent 修 GSAP timeline |
| render | `--strict` 模式,任何 lint 错误立即停止 | 回退到 lint 步骤 |

**失败重试策略**:

- 每步最多自动重试 3 次(由 `scripts/lint.py` 等脚本内部处理)
- 3 次仍失败 → 推送 `video.quality_gate` 事件携带 `errors[]` 到前端,聊天面板显示具体错误,等待 agent 修复
- agent 修复后从失败步骤继续,不重头跑(避免重复劳动)
- 渲染中断(进程崩溃/网络断开)→ 保留中间帧 → 用户可选择"断点续渲"或"重头开始"

**WebSocket 事件协议**:

```jsonc
// WS event: video.quality_gate
{
  "project": "promo-2026q3",
  "step": "lint|validate|inspect|render",
  "status": "running|passed|failed",
  "attempt": 1,
  "errors": [
    { "scene": "scene_03", "line": 42, "rule": "clip-missing-data-start",
      "message": "Element <div class=\"clip\"> missing data-start attribute" }
  ],
  "stats": { "scenes": 8, "clips": 42, "duration": 32.5, "fps": 30 }
}
```

### 2.3 HTML 场景生成规范

#### 2.3.1 Hyperframes 契约(必须遵守)

基于调研,agent 生成的 HTML 必须满足:

1. **根 composition** 有 `data-composition-id`、`data-width`、`data-height`、`data-duration`
2. **所有定时元素** 加 `class="clip"` + `data-start` + `data-duration` + `data-track-index`
3. **GSAP 时间线** `paused: true`,注册到 `window.__timelines[composition-id]`
4. **同轨道不能时间重叠**

### 2.7 打包体积评估(2026-07 实测)

> 本节基于 npm registry 精确 unpackedSize 字段 + Mona 1.3.0 NSIS 实际体积 136.43 MB 的基线测算。

#### 2.7.1 Hyperframes 依赖体积明细

**npm 依赖**(`npx hyperframes` 首次执行后写入 `~/.npm/_npx/`):

| 组件 | unpacked 大小 | 占比 | 说明 |
|------|--------------|------|------|
| `hyperframes` CLI 本体 | 22.7 MB | 6.4% | 含 @hyperframes/{core,engine,producer,studio} |
| **`onnxruntime-node`** | **258.4 MB** | **73%** | ⚠️ beat-analyzer + background-removal 用,CPU 版捆绑三平台二进制 |
| `@img/sharp-win32-x64` + `libvips` | 38.4 MB | 10.8% | 图像处理 |
| `@esbuild/win32-x64` | 11.7 MB | 3.3% | JS 打包器 |
| `prettier` | 8.4 MB | 2.4% | lint 格式化 |
| `fontkit` | 5.6 MB | 1.6% | 字体度量 |
| `puppeteer-core` + `@puppeteer/browsers` | 6.1 MB | 1.7% | Chrome 下载器 |
| 其余 ~10 个小依赖 | ~2 MB | 0.6% | hono / citty / debug / adm-zip 等 |
| **npm 依赖合计(未压缩)** | **~354 MB** | 100% | 7z 压缩后约 140–180 MB |

**运行时二进制**(由 `video_runtime.py` 下载到 `<userData>/runtime/`):

| 组件 | 下载大小 | 解压大小 | 缓存路径 |
|------|---------|---------|---------|
| Chrome Headless Shell (Win x64) | 108 MB | ~280 MB | `~/.cache/hyperframes/chrome/` |
| Node.js 22 (Win x64) | 30 MB | ~70 MB | `<userData>/runtime/node/` |
| FFmpeg (BtbN GPL build) | 80 MB | ~100 MB | `<userData>/runtime/ffmpeg/` |
| 背景移除模型 u2net(可选) | 168 MB | 168 MB | `~/.cache/hyperframes/models/` |
| **运行时合计** | **~386 MB** | **~618 MB** | 不进安装包 |

#### 2.7.2 集成方案对比

| 方案 | 安装包增量 | 首次使用体验 | 适用场景 |
|------|----------|------------|---------|
| **A. 完全按需下载**(推荐默认) | **+0 MB** | 首次需下载 ~386 MB 到 `<userData>/runtime/` | Phase 3 默认实现 |
| **B. 全量打包**(含 onnxruntime + 模型) | **+250 ~ 320 MB** | 开箱即用,NSIS 翻倍至 ~400 MB | ❌ 违反精简原则 |
| **C. 精简打包**(剔除 onnxruntime + 模型) | **+40 ~ 60 MB** | npm 依赖内置,首次仅下载 Chrome/FFmpeg/Node | 可选增强,Phase 3.x |
| **D. 仅打包 hyperframes-cli**(无依赖) | **+10 MB** | 首次 npx 自动拉取依赖(慢) | ❌ 不推荐 |

#### 2.7.3 决策

**Phase 3 默认采用方案 A**:

- 沿用 [video_runtime.py](../../mona/api/video_runtime.py) 现有按需下载机制
- 首次创建视频项目时弹窗提示用户下载缺失组件
- **安装包零增量**,NSIS 体积保持 1.3.0 基线 136.43 MB

**Phase 3.x 可选增强(方案 C)**:

- 在 NSIS 打包阶段把 `hyperframes` CLI + npm 依赖(剔除 `onnxruntime-node` 和背景移除模型)塞进 `src-tauri/resources/hyperframes-runtime/`
- 增量约 **+40 MB**(7z 压缩后),NSIS 体积从 136 → 176 MB
- 用户首次仅需下载 Chrome(~108MB)和 FFmpeg(~80MB),共 188 MB
- 节拍检测 / 背景移除仍按需单独下载 `onnxruntime-node`(~258MB)

**禁止方案 B**:

- `onnxruntime-node` 258MB 中绝大部分是跨平台二进制(同时含 win32/darwin/linux),单平台用户用不到的部分纯属浪费
- 背景移除模型 u2net 是 168MB 的可选权重,默认不下载
- 违反项目规则"Mona Desktop 必须完全自包含但不盲目堆砌"

#### 2.7.4 体积控制红线

- **NSIS 安装包上限 200 MB**(当前 136 MB + 上限 64 MB 增量预算)
- 超出时优先剔除顺序:`onnxruntime-node` > 背景移除模型 > prettier > fontkit
- 用户首次使用体验:从"打开视频 tab"到"能预览第一个 scene" < 30 秒(已下载依赖后)
- 用户首次完整渲染:从"按渲染按钮"到"看到 MP4" < 视频时长的 3 倍
- 依赖下载支持断点续传 + SHA256 校验 + 失败重试(最多 3 次)

#### 2.7.5 现有 mona-gateway 中的潜在复用

调研发现 `mona-gateway/_internal/playwright/driver/` 内已包含 `node.exe` (87 MB,Playwright 自带的 Node.js runtime)。技术上可考虑复用,但有以下风险:

- Playwright 内嵌 node 是给 playwright-driver 用的,单独取出跑 hyperframes-cli 可能版本/ABI 不匹配
- PyInstaller 产物路径对外部进程暴露不便
- 升级 Playwright 时 node 版本可能变化,影响 hyperframes 兼容性

**决策:不复用**,维持方案 A 独立下载 Node.js 22。后续若用户反馈下载负担过重,再评估复用方案。

#### 3.2.2 postMessage 协议实现

```typescript
// 完整的 JSON 协议封装
class DrawioProtocol {
  private iframe: HTMLIFrameElement;
  private listeners: Map<string, Function[]> = new Map();

  constructor(iframe: HTMLIFrameElement) {
    window.addEventListener("message", this.onMessage);
  }

  // 发送 action
  send(action: string, data: object = {}) {
    this.iframe.contentWindow!.postMessage(
      JSON.stringify({ event: "configure", ...data, action }),
      "*"
    );
  }

  // 监听 event
  on(event: string, callback: Function) { ... }

  // 便捷方法
  load(xml: string) { this.send("load", { xml }); }
  export(format: string) { this.send("export", { format }); }
  layout(type: string) { this.send("layout", { layouts: [{ type }] }); }
}
```

## 五、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Hyperframes 依赖 Node.js 22+,Mona 无 Node 运行时 | 视频功能不可用 | 延迟下载 Node.js 22 到 `<userData>/runtime/node/`(下载 30MB / 解压 70MB),首次使用提示 |
| draw.io webapp 体积大(~50MB) | 安装包变大 | 只打包核心文件,排除测试/文档/示例 |
| Chrome Headless Shell 下载 108MB / 解压 280MB | 用户首次使用体验差 | 必须用户确认,显示进度,支持取消,断点续传 + SHA256 校验 + 失败重试(3次) |
| `onnxruntime-node` 258MB 是 npm 依赖体积瓶颈 | 若全量打包则 NSIS 翻倍至 ~400MB | 默认方案 A 不打包(零增量),方案 C 剔除该依赖(增量 +40MB),节拍检测/背景移除按需单独下载 |
| Hyperframes CLI 未文档化 PUPPETEER_EXECUTABLE_PATH | 无法指定系统 Edge | 优先用 `hyperframes browser ensure` 自管理 Chrome |
| draw.io embed 自托管可能协议不完整 | load/save/export 可能异常 | 打包官方 release 版本,充分测试 JSON 协议 |
| 视频/流程图 agent 生成的产物质量不稳定 | 用户体验差 | 质量门禁(lint→validate→inspect→render --strict)+ soul prompt 严格约束 |
| 渲染中断(进程崩溃/网络断开) | 用户进度丢失 | 保留中间帧,支持"断点续渲"或"重头开始" |

## 七、决策记录

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 视频渲染引擎 | Hyperframes | agent 友好(HTML+GSAP),面向 coding agent 设计 |
| Node.js 运行时 | 延迟下载到 `<userData>/runtime/node/`(30MB/70MB) | 零配置红线 + 不影响安装包体积 |
| Chrome 依赖 | `hyperframes browser ensure` 自管理(108MB/280MB) | 官方推荐,兼容性最好 |
| 质量门禁 | lint→validate→inspect→render --strict 全流程 | 质量优先,不跳过任何步骤 |
| Hyperframes npm 依赖打包策略 | **方案 A(默认零增量)+ 方案 C(可选 +40MB)** | onnxruntime-node 258MB 是体积瓶颈(占 npm 依赖 73%),提供节拍检测/背景移除为可选,打包阶段剔除;NSIS 上限 200MB |
| 复用 mona-gateway 内 Playwright node.exe | **不复用** | 版本/ABI 可能不匹配,PyInstaller 路径对外暴露不便,升级风险高 |
| 失败重试 | 每步最多 3 次,从失败步骤续跑 | 避免重复劳动,保留中间帧支持断点续渲 |
| 流程图编辑器 | draw.io embed (iframe+postMessage) | 成熟、功能完整、支持二次编辑 |
| draw.io 部署 | 本地静态文件打包 | 完全离线,满足零配置红线 |
| 自动布局 | draw.io 内置 layout action | 无需额外依赖,算法丰富 |
| 聊天面板 | 抽取 DocChatPanel 通用组件 | 复用 PPT 成熟模式,避免重复 |
| mxGraph XML 生成 | agent 生成 graph.json → build_xml.py 转换 | agent 不直接写 XML,降低出错率 |
