# AI 侧边栏价值评估与最小重设计方案

> 范围：终端、邮件、数据库、笔记 4 个模块
> 更新日期：2026-07-26
> 状态：实施建议稿
> 依据：当前代码静态检查；尚无用户频率、转化率和时延数据

---

## 1. 结论

Mona 的模块 AI 应继续围绕三件事建设：

1. **拿到当前对象的正确上下文**
2. **把结果直接作用回当前模块**
3. **所有高影响动作保留用户确认**

当前最值得先补的不是统一框架，而是两个尚未闭环的高价值场景：

- **邮件**：让 Agent 看见当前邮件正文和已有分析结果，并能把回复草稿回填写信窗口。
- **笔记**：让 AI 直接处理用户选中的文本，而不是强制整篇笔记进入侧边栏对话。

第一阶段不建设 `AgentDock`、模块 manifest、通用卡片注册表或统一会话 hook。现有项目已经共享 `useMonaStream`、`useSessionHistory` 和 `ThreadMessages`；剩余差异主要是各模块真实业务差异，不应先被抽象掉。

## 2. 已验证的现状

### 2.1 共用基础已经存在

终端、邮件、数据库都复用了 `ThreadMessages`，四个模块都基于 `useMonaStream` 和 `useSessionHistory` 处理流式响应及历史记录。因此，“四套 AI 基础设施完全重复”不准确。

当前重复主要集中在：

- Header、输入框和发送快捷键
- 新会话创建与 pending prompt
- 模块上下文拼接
- 快捷操作和结果应用

前两项可以在行为稳定后提取小型共享组件；后两项应继续留在模块内。

### 2.2 四个模块的真实差异

| 模块 | 会话作用域 | 当前上下文 | 已有行动闭环 | 当前主要缺口 |
|------|------------|------------|--------------|--------------|
| 终端 | 面板挂载时创建临时会话 | 当前 session + buffer 尾部 4000 字符 + execMode | Agent 执行命令、报告文件回传 | 命令解释、错误诊断等轻场景 |
| 邮件 | 全局 `agentChatId` | 当前邮件元信息；不含正文和分析结果 | 批量操作建议经确认后执行 | 上下文割裂、切换邮件可能混入旧会话、写信侧无 AI |
| 数据库 | 每个查询 tab 一个会话 | 连接、库、当前表、错误；NL2SQL 仅当前表列结构 | 提取 SQL 并回填编辑器 | 多表上下文、结果仍依赖文本提取 |
| 笔记 | 每篇笔记一个会话 | 自由问答最多注入 12000 字符；部分快捷操作在 Tauri 下走临时文件 | 追加、替换、复制、存为新笔记 | 选区级 AI、上下文策略不统一 |

### 2.3 邮件的两条 AI 链路

邮件当前有两条独立链路：

1. `email_analyze`：读取正文和图片，生成摘要、分类、意图、紧急度等结果，并持久化到 SQLite。
2. Agent 会话：通过 `[EMAIL_CONTEXT]` 注入账号、文件夹、UID、主题、发件人和日期。

问题不是需要删除其中一条，而是两条链路没有共享结果。正确方向是**联通结果，保留各自职责**：

- `email_analyze` 继续负责结构化分析和本地缓存。
- Agent 在回答当前邮件问题时复用已有分析，并按需读取经过限制的正文。

### 2.4 当前结果协议并不统一

各模块的结果来源不同：

- 邮件从 trace 文本中提取操作 JSON。
- 数据库从 Assistant Markdown 中正则提取 SQL。
- 终端通过独立 Tauri 事件接收报告文件。
- 笔记直接对 Assistant Markdown 提供追加、替换等操作。

因此，当前不具备直接建设通用 `CardRenderer` 的稳定输入协议。应先在模块内完成两种结果卡片，验证结构后再判断是否值得统一。

## 3. 优先级判断

以下“高频”判断目前都是产品假设，不是已验证事实：

- 邮件用户最需要草拟回复。
- 笔记用户最需要选区润色。
- 终端用户更常解释错误，而不是运行完整巡检。

在缺少使用数据时，优先级按以下条件确定：

1. 当前链路是否明显断裂
2. 是否能复用已有能力
3. 是否能独立交付和撤回
4. 是否不扩大安全边界

据此，邮件上下文与写信 AI、笔记选区 AI 进入 P0；统一框架不进入 P0。

---

## 4. 设计边界

### 4.1 P0 不改 Agent 核心协议

P0 继续使用现有文本 prompt 和 `SendOptions`。上下文可在前端显示为静态芯片，但不引入结构化 envelope。

如果未来需要 `{type, ref, summary, contentRef}` 这类真实结构化上下文，必须单独立项，明确修改：

- 前端 `SendOptions`
- WebSocket 消息格式
- 后端 channel 消息解析
- context builder
- 历史记录兼容策略

这不是“仅前端改造”。

### 4.2 不建立模块 manifest

当前只有四个固定模块，没有运行时插件加载需求。各模块直接组合共享 UI 组件，比 manifest、registry 和 provider 接口更短、更容易调试。

满足以下任一条件后再考虑 manifest：

- 出现第 5 个模块，且重复接入成本明显
- 需要第三方模块运行时注册 AI 能力
- 三个以上模块已经稳定共享同一上下文或结果协议

### 4.3 保留安全闸

- 写信 AI 只回填草稿，不自动发送。
- 终端生成命令只写入输入行，不自动执行。
- SQL 默认只插入编辑器，不提供“仅凭 SELECT 判断安全”的自动执行。
- 批量邮件操作继续显示目标列表并要求确认。
- 建索引、DDL 和可能产生高负载的数据库动作不进入本轮。

### 4.4 任何结构化结果都必须可降级

卡片解析失败或收到未知类型时，继续显示原始 Markdown，不得丢失结果或阻断会话。

## 5. P0-A：邮件闭环

P0-A 只解决当前邮件理解和写信回填，不重构其他模块。

### 5.1 联通已有邮件分析

当用户针对当前邮件提问时，prompt 按以下顺序构建：

1. 邮件身份：账号、文件夹、UID、主题、发件人、日期
2. 已有分析：摘要、分类、意图、紧急度、关键信息
3. 正文：优先纯文本，去除明显 HTML；设置单一硬上限
4. 用户问题

初始正文上限采用 **4000 字符**，作为可调整常量，不建设配置界面。上线后根据失败率、费用和回答质量决定是否调整。

已有分析不存在时不自动触发后台批量分析；直接使用当前正文回答。用户点击“内容分析”后，结果进入缓存，并在后续提问中复用。

### 5.2 明确会话作用域

邮件需要区分两类任务：

- **当前邮件任务**：总结、提取待办、草拟回复。使用当前邮件作用域；切换邮件不得继续携带上一封邮件正文。
- **邮箱级任务**：搜索、自动归档。继续使用邮箱级 Agent 会话，不隐式绑定某一封邮件。

UI 不增加复杂模式页。入口本身决定作用域：

- 当前邮件区域发起的动作进入当前邮件作用域。
- “自动归档”和无选中邮件时的搜索进入邮箱作用域。

### 5.3 写信侧 AI

首版只提供两个动作：

1. **草拟回复**：根据原邮件和当前收件人关系生成正文。
2. **润色正文**：处理写信窗口中已有内容。

语气要求通过一个简单选择项传入 prompt，不建设模板系统。

结果只回填编辑器，并满足：

- 不自动发送
- 保留用户原始正文，可撤销
- 回复模式下不修改收件人、主题和附件
- 生成失败不清空当前草稿

### 5.4 P0-A 验收标准

- Agent 能回答只存在于当前邮件正文中的问题。
- 已存在的 `email_analyze` 结果被复用，不再次请求同一分析。
- 切换邮件后，新请求不携带上一封邮件正文。
- 草拟回复和润色都只修改正文，不触发发送。
- 取消或失败时原草稿保持不变。
- 邮件批量操作的确认流程无回归。

---

## 6. P0-B：笔记选区 AI

P0-B 独立于邮件和共享外壳，可单独提交。

### 6.1 入口

复用现有 Markdown 编辑器的选区能力。用户选中文本后显示轻量工具条，首版只提供：

- 润色
- 缩写
- 翻译

扩写、续写和自定义模板暂不进入首版；已有侧边栏模板继续保留。

### 6.2 上下文

发送给 Agent 的内容只包含：

1. 笔记标题
2. 选中文本
3. 动作要求

不默认发送整篇笔记。只有后续验证发现选区缺少语境时，再增加选区前后有限文本。

### 6.3 结果应用

结果以小型预览呈现，提供：

- 替换选区
- 插入选区后
- 复制
- 取消

替换前必须确认当前选区仍与请求时一致；如果用户等待期间修改了正文，则禁止自动替换，保留复制结果。

### 6.4 P0-B 验收标准

- Agent 收到的正文仅包含请求时的选区。
- 替换只影响原选区，不改动其他段落。
- 生成期间编辑正文不会替换错误位置。
- 用户可以撤销一次替换。
- 切换笔记后，旧结果不能作用到新笔记。
- 现有整篇总结、翻译、标签和自定义模板无回归。

---

## 7. P1：模块内结果卡片

P1 先做两张卡，不建设全局卡片框架。

### 7.1 邮件分析卡

复用现有 `EmailAnalysis` 数据，展示：

- 摘要
- 分类、意图、紧急度
- 关键信息
- 草拟回复

“存为笔记”“创建日程”等跨模块动作暂不加入。

### 7.2 NL2SQL 卡

展示：

- 生成的 SQL
- 插入编辑器
- 替换当前编辑器内容
- 复制

不提供直接执行。当前 SQL 仍可由用户在数据库编辑器中检查并运行。

### 7.3 P1 验收标准

- 非法或未知结果自动回退到 Markdown。
- 卡片按钮只操作当前模块和当前对象。
- SQL 卡不会自动执行查询。
- 邮件卡不会自动发送或批量修改邮件。

## 8. P2：小范围 UI 统一

P0、P1 行为稳定后，再提取以下无业务组件：

- `AgentPanelHeader`
- `AgentComposer`
- 只读 `ContextChip`

统一内容：

- Header 高度和标题布局
- Enter 发送、Shift+Enter 换行
- 发送、停止、重置按钮样式
- 输入框基础样式

不统一：

- chatId 的存储位置
- 会话创建策略
- prompt 构建
- 快捷操作
- 结果应用
- 确认流程

不新增 `useScopedAgentChat`。只有当至少三个模块的会话生命周期真正相同，且共享代码能明显减少分支时，再考虑提取 hook。

## 9. 暂缓项

以下项目当前没有足够证据或依赖更大改造，本轮不实施：

| 项目 | 暂缓原因 | 重新评估条件 |
|------|----------|--------------|
| 通用 AgentDock + manifest | 现有模块差异大，已有共享流式基础 | 第 5 个模块或运行时插件接入 |
| 结构化 context envelope | 需要跨前后端协议变更 | 文本上下文出现稳定性或容量问题 |
| 通用 CardRenderer | 尚无统一工具结果协议 | 至少 3 种卡片共享稳定 schema |
| 主动建议 | 需要事件去重、关闭策略、成本和隐私设计 | 被动入口使用率得到验证 |
| 高优先级邮件自动分析 | 当前分析为人工触发，会增加后台成本 | 用户明确开启且成本可控 |
| 跨模块“发送到…” | 涉及授权、目标选择和失败恢复 | 单模块闭环稳定后 |
| 一键创建索引 | DDL 权限、锁和负载风险高 | 有完整预览、确认和回滚方案 |
| SQL 直接执行 | “仅 SELECT”不是充分安全边界 | 有查询成本预估和数据库级限制 |
| 执行计划可视化、ghost text | 体验增强，不影响当前核心闭环 | P0/P1 已验证价值 |

## 10. 交付顺序

| 阶段 | 内容 | 修改范围 | 是否依赖其他阶段 |
|------|------|----------|------------------|
| P0-A | 邮件分析联通、正文上下文、会话作用域、写信 AI | 邮件模块 | 否 |
| P0-B | 笔记选区 AI | 笔记与通用 Markdown 编辑器 | 否 |
| P1-A | 邮件分析卡 | 邮件模块 | P0-A |
| P1-B | NL2SQL 卡 | 数据库模块 | 否 |
| P2 | Header、Composer、只读 ContextChip | 共享 UI + 逐模块迁移 | P0/P1 稳定 |

每个阶段独立 PR、独立验收。P0-A 与 P0-B 可并行，不要求先完成任何统一框架。

---

## 11. 验证方式

当前没有代码使用数据支持“最高频”判断。首轮不为此新建遥测系统：

- 如果项目已有埋点，复用已有能力记录动作展示、生成、应用、取消、失败和时延。
- 如果没有埋点，使用固定任务清单做人工可复现测试，并收集首批用户反馈。

每个实现 PR 至少包含：

1. 对新增 prompt 构建或结果解析逻辑的一项可运行测试
2. 项目 build/compile 通过
3. 相关模块测试通过
4. 一次真实 UI 操作链路验证
5. 安全闸和失败回退验证

---

## 12. 最终决策

本轮采用“先补闭环、后做抽象”的路线：

- 先让邮件 Agent 真正理解当前邮件并帮助写信。
- 先让笔记 AI 在选区处完成工作。
- 再把已经稳定的结果做成模块内卡片。
- 最后只提取确定相同的 UI。

统一协议、插件框架和主动助手都不是当前交付这两个价值闭环的前置条件。
